# WP-0.2v DCTDecode images in the Tier E tracer

## What changed

- `mag/Cargo.toml`: `zune-jpeg = "0.5"`, `zune-core = "0.5"` (both were
  already in `Cargo.lock` through typst, 0.5.15 / 0.5.3; the lock gains
  only the two root dependency lines, nothing is downloaded).
- `mag/src/parity/streams.rs`:
  - `decode_stream` handles `DCTDecode` through `dct`: zune-jpeg in strict
    mode, scalar path (`set_use_unsafe(false)`, so no SIMD-dependent
    rounding), output colour space = the JPEG's own, so the decoder never
    colour-converts. YCbCr and YCCK get one explicit YCC-to-RGB transform
    (JFIF coefficients, f64, round, clamp); K passes through. Luma, RGB
    and CMYK samples pass through raw. Baseline and progressive both
    decode (zune). Any other JPEG colour space bails.
  - The Adobe marker never inverts anything: the samples are the DCT
    filter output, as the PDF defines it. Inversion comes only from the
    image's `/Decode` array, which is now honoured: each pair must be
    `[0 1]` (identity) or `[1 0]` (sample -> 255 - sample); any other pair
    or a wrong length fails loud (before: anything but identity failed).
    This applies to every image and SMask, not only JPEG.
  - Image colour spaces: DeviceGray, DeviceRGB, the sRGB/sGrey v4 ICC
    profiles (unchanged) plus DeviceCMYK. A CMYK ICC profile, Lab,
    Indexed etc. still fail loud. A `/ColorTransform` in DecodeParms
    fails loud (override not implemented).
  - Pixel identity: grey and RGB images hash the same RGBA bytes as
    before (so every existing hash is unchanged). CMYK images hash
    `"DeviceCMYK"` + CMYKA bytes, a separate domain from RGBA, mirroring
    how paint colours keep the cmyk family.
- Fixture `mag/tests/parity_jpeg/` (16x16, 5.7 KB total), generated by a
  scratch script with Pillow 12.3 and libjpeg-turbo 3.1.1: `rgb.jpg`
  (q90, 4:2:0), `rgb-prog.jpg` (`jpegtran -progressive` of it, same
  coefficients), `rgb-q60.jpg` (same source, q60), `rgb-alt.jpg` (source
  with one pixel changed), `rgb444.jpg` + `rgb444.ppm` and `grey.jpg` +
  `grey.pgm` (djpeg reference decodes), `cmyk.jpg` (Pillow, Adobe
  transform 0, stored inverted), `ycck.jpg` (Adobe transform 2, built
  from the same CMYK values).
- Tests (streams.rs):
  - `a_jpeg_decodes_to_libjpeg_samples_and_hashes_as_those_pixels_under_any_filter`:
    samples within 2 (RGB 4:4:4) and 1 (grey) of libjpeg-turbo's djpeg,
    an independent decoder (measured max 2 and 1); the DCT image hashes
    equal to an unfiltered image carrying the same samples.
  - `one_picture_compares_equal_across_encodings_of_its_pixels_and_unequal_otherwise`:
    baseline == progressive (same pixels); q90 != q60; one changed source
    pixel != ; 4:2:0 != 4:4:4.
  - `adobe_inverted_cmyk_and_ycck_read_as_cmyk_through_an_inverting_decode_array`:
    with `/Decode [1 0 1 0 1 0 1 0]` both `cmyk.jpg` (within 2) and
    `ycck.jpg` (within 3) give the authored CMYK values; without it the
    samples are exactly the inverse and the hash differs; the result
    hashes equal to an unfiltered DeviceCMYK image of the same samples.
  - `a_jpeg_outside_the_accepted_colour_spaces_or_decode_arrays_fails_loud`:
    CMYK JPEG declared DeviceRGB, Lab, Decode `[0 2 ...]`, ColorTransform,
    truncated stream.

Re-encoding at another quality FAILS the comparison (test above). That is
correct per Tier E: the decoded pixels differ, and Tier E compares
pixels. The plan does not say otherwise.

## What is and is not proven

- Proven: the tracer decodes baseline and progressive JPEG, grey, RGB,
  CMYK and YCCK, honours identity and inverting Decode arrays, and
  produces the same pixel identity as an unfiltered image of the same
  samples; same pixels compare equal, a re-encode or one changed pixel
  compares unequal; out-of-scope colour spaces, Decode pairs and
  ColorTransform fail loud. Decoded values agree with libjpeg-turbo to
  within 2 levels on the fixtures. No floor row and no 010 verdict byte
  moved. `--adhoc 008` now reaches a verdict.
- Not proven: agreement with any reference renderer beyond +-2 levels
  (zune's IDCT and my YCC transform are not libjpeg's bit for bit; both
  legs share the decoder, so equality is unaffected). JPEG with
  arithmetic coding, 12-bit, or lossless is unsupported by zune and would
  fail loud (not exercised). A DCT image whose component ids are 'R','G','B'
  is treated as RGB (zune's rule) regardless of the PDF default
  ColorTransform. The YCCK fixture is synthetic (patched Adobe byte),
  not a Photoshop file.
