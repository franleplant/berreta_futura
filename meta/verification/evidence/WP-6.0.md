WP-5.1c recorded mismatches 1 and 2 as "deliberately approximated". They were
real divergences on the translation path, and the Rust port was wrong, so they
are fixed. Against HEAD, the three cases fail in `cases_match_the_python_loader`
with the Rust outputs in the table. After the fixes, every case matches.

**Declared divergence, not a mismatch.** WP-5.12 made the translation `raw`
figure `path` source-relative (`media/d.png`). Python still writes the resolved
absolute path. The comparison strips `<ROOT>/library/sources/<source_id>/` from
Python's value, and only there. `python_writes_translated_figure_paths_absolute_where_rust_keeps_them_source_relative`
pins exactly which cases need the rewrite (2 synthetic cases, plus 906 es in the
real test). If Python ever stops diverging, that test fails.

**Oracle harness changes.** The generator is WP-5.1c clause 5's script with two
edits. Figure `path` is dumped root-relative, where it used to be an absolute temp
path that no two runs share. `raw` has the root scrubbed to `<ROOT>` the same way
error strings are. Regeneration stayed purely additive: `git diff --numstat`
shows `336 0` on the expected file, so no pre-existing case changed. The two new
YAML-parser-message cases join `PARSER_DIAGNOSTIC_CASES`. They are compared up to
the parser's own diagnostic, as the base-path pair already was.

Negative controls: a one-word edit to `translation_media_fields`' expected message
gives `1 cases diverge: translation_media_fields`. Editing 906's expected title
fails `906 es diverges`. Editing one 004-variant block count fails `004 es
diverges`. After the fixes, the edition 010 loader oracle (WP-5.1c clauses 1-4,
restaged) is still EQUAL (12,926 bytes).

### Unicode-table pin

Where it lives:
- `mag/src/model/shared.rs:188` `FOLD_DATA` (1,530 entries), used by `py_casefold`.
- `mag/src/model/shared.rs:190` `UPPER_DATA`, used by `py_upper`.
- `mag/src/critic/text.rs:12` `LOWERCASE_RANGES`, the critic's islower filter.
- Users: `model/manifest.rs` (now 12 casefold sites), `cover/text.rs`,
  `typeset/cover.rs`, `web/edition.rs`, `critic/text.rs`. The full-plane pins are
  `cover_text.rs::casefold_matches_python_over_all_codepoints` and the islower and
  isspace expected files.
- `is_python_space` is not a table. It is `is_whitespace` + U+001C-U+001F.

Measured over all 1,112,064 scalar values (a scratch `rustc` dump of std,
compared in Python). The three pinned tables equal CPython 3.12's
`str.casefold/upper/islower` on every scalar value.

| operation | pinned (Py 15.0.0) vs Rust std 17.0.0 | codepoints differ | in magazine text (310 distinct chars, 202 non-ASCII, all tracked editions/library/fixture text) |
|---|---|---|---|
| upper | `UPPER_DATA` vs `to_uppercase` | 55 (U+019B, U+0264, U+1C8A, U+A7CD..A7DB, Garay U+10D70-85, U+16EBB-ED3) | **0** |
| lowercase, version only | `str.lower` vs `to_lowercase` | 55 | **0** |
| islower | `LOWERCASE_RANGES` vs `is_lowercase` | 53 | **0** |
| isspace | `str.isspace` vs `is_python_space` | 0 | 0 |
| casefold | `FOLD_DATA` vs `to_lowercase` (std has no casefold) | 352 | **1: U+00B5 MICRO SIGN** (casefold gives μ, lowercase keeps µ), in 2 library sources and 008's run |

**Recommendation.** Unpin `upper` and `islower` to std. The difference is the
Unicode version only, no character the magazine has ever printed is affected,
and two tables and their pinning tests go away. Keep `FOLD_DATA`, and say why:
std has no casefold, and replacing casefold with `to_lowercase` changes the
algorithm, not the version (ß, µ, final sigma and 349 more). Casefold is the
correct operation for the caseless matches it serves (byline, title containment,
plate and web filename uniqueness). The table can be regenerated from a newer
CaseFolding.txt if that is ever wanted.

## What is and is not proven

PROVEN: on 39 translation cases, 906 es and two 004 translations, the Rust
translation loader matches Python's structure and every refusal message. The one
exception is the declared, pinned figure-path divergence, where Python is wrong.
Every literal refusal site reachable from `load_translation` fires in at least
one translation case. Three real port defects (casefold, strip, splitlines) were
found and fixed. 906 es renders on Typst without Python and still passes adhoc
parity at Tier E.

NOT PROVEN:
- The 004 translation never loads successfully on either side. Its committed
  English manuscripts are not the ones it was translated from. The OK path is
  proven on 906 and synthetic cases only.
- `.resolve()` symlink semantics are still approximated lexically (WP-5.1c).
- `records.rs` capture-side `.trim()` calls (below line 650: URL, tags, synopsis)
  still use Rust `trim`. They are outside the translation path and not checked
  here.
- Equality with Python is not correctness. Where Python itself is wrong (as with
  the figure path), both could agree on a bad value in a case no one built.
