Everyone is renting the same brain now. A software travel agent answered a simple trip question with an exchange rate, a weekly temperature, and museum hours. It sounded clean and useful. All of it was invented. The search tool had returned nothing, so the model filled the gap and passed its invention off as a lookup. Across 100 real sessions, response quality was 83.9% and faithfulness was 32.3%. The agent wrote beautifully and told the truth about a third of the time.

A better model would not have caught this. The missing layer decides whether an answer was right and changes what runs next. A thermometer tells you the room is cold. A thermostat turns the heat on. Most teams have the thermometer: a dashboard, or a Friday afternoon spent scrolling through outputs and deciding that things seem worse. Eval engineering is the wiring from the reading to the furnace.

The useful order is simple. Loops came first, then graphs, then evals. An agent in a loop could try, inspect what came back, and try again. A graph let independent work run side by side. Evals decide whether that speed was worth having. Twenty agents reporting to one frozen judge create twenty times as many places for a wrong answer to look finished. The model is a rental. The examiner is yours, and every failure you feed it stays there.

## Make the score change the run

A number in a report has no path back to the execution it measured. “A score that never changes behavior is analytics. An eval that changes the next edge is engineering.”

That wiring turns verdicts into routing decisions. Low context recall rejects a handoff. Bad tool use retries or swaps the node. A hallucination quarantines the branch. A schema failure blocks the edge. Compliance risk routes to human review. Verified completion terminates the run. For the travel agent, an empty search result should force an admission of uncertainty rather than another polished invention.

The judge needs rules too. One evaluation team runs Sonnet as judge for output generated by Haiku, because a model grading its own family can share its blind spots. The working rubric is one observable condition: `Pass iff [the independently observable successful outcome]`. The judge handles semantic calls; ordinary code handles whether a test passed, a file exists, or state changed. Response length, keywords, citation counts, exact phrasing, tool-call counts, and similarity to a reference are poor substitutes for success. Pin the judge and log its version, or a silent upgrade will make a month of scores impossible to compare.

Optimize against a judge long enough and the agent learns to look right rather than be right.

## Install the examiner around the case

A new platform is optional. In one blind test, researchers took 100 production traces from a live voice agent, had a human expert label 39 kinds of failure, hid those labels, and gave the same cases to evaluation systems. Braintrust Loop recovered 87.2% of the human-flagged failures. Codex on GPT-5.5 High reached 84.6% recall and 82.8% precision, above LangSmith at 79.5% and close to dedicated tools. A coding agent already on the subscription produced comparable results.

## Turn failures into permanent tests

Invented tests protect against failures imagined at a desk. The expensive failures already sit in the logs. A useful first set contains 25 complete traces with good and bad behavior beside each other: a normal request, a user-confirmed success, a correction or rephrasing, a failed or repeated tool call, and an external failure such as a timeout or rate limit.

Each finding records observed behavior, comparison, attribution, and an eval candidate. Attribution prevents wasted effort. The same lookup twice with identical arguments is your agent looping. A 429 is somebody else's limit unless your agent was supposed to recover from it. For the travel agent, the empty search result becomes a test of whether the response stays faithful to the tool output.

Each capability then gets a folder such as `evals/<task-id>/` containing `task.toml`, `instruction.md`, `environment/`, and `tests/`. The tested agent sees the instruction and environment; the expected outcome, rubric, and judge credentials remain hidden. Recorded answers describe what happened, not what should have happened, so the answer key comes from tests, source records, policy, known state, or a person. The verifier earns trust only after it sends one clearly correct result and one plausible wrong result in the right directions. The environment must not reveal the answer before the agent reaches the tool. Anything that costs money or writes to production gets simulated.

The starting instruction asks the coding agent to use the eval-engineering skill, map the repository's agent and backing data, read the 25 traces, propose candidates grounded in actual failures, recommend one, and wait before implementing. The interview matters because the definition of correct lives in the team's head and nowhere in the model. Repeated often enough, each incident becomes a permanent test.

## Let safe work merge itself

Every pull request an agent opens otherwise lands in a human queue. A confidence score can combine deterministic guardrails, the recent eval trajectory for that agent, its historical revert rate on this repository and change class, and the sandbox result. A score above the threshold permits an automatic merge. A lower score sends a human the failing signal, so review begins at the problem.

Trust in an agent is an actuarial calculation. In one production system, 19 of every 20 pull requests from a fully autonomous agent merged without human involvement. Across top agents, about three quarters of merged work required no human edit, reverts stayed in the low single digits, and guardrails rejected one pull request in five before review.

The constraint is the product. One team ran 285 iterations of a self-improving codebase, merged 1,094 pull requests, and had zero regressions, yet 38 green tests coexisted with a completely broken product. A suite can go green while the product falls apart, so the loop has to converge on the specification rather than the score.

The cautious rollout is shadow mode for at least four hours of real traffic, with the gate closed when automated and human verdicts differ by more than 2%. Sampling 1% to 5% of traces avoids the cost of full capture. With the risky slice gated and the boring 80% open, a two-person shop can take on work it once declined. The model bill does not move. Everything else does.

## The evals that repay the afternoon

Faithfulness, tool-parameter accuracy, and response quality are a working default for any tool-using agent. For code changes, production teams score intent and decision, execution and artifact, completeness and usefulness, instruction and boundary, and efficiency. The dataset type matters: `final_response` measures the answer alone, `single_step` one decision, `trajectory` the whole path, and RAG retrieval quality. A final answer can be correct even when the path was broken.

A living suite holds 300 to 800 cases, with 500 running in under five minutes. Its first five failures are an empty tool result that must not become an invented number, a repeated call, a boundary refusal, handoff integrity, and verified completion based on a real signal. Three measurements, one dataset type, and five evals fit in an afternoon. The suite grows more valuable each week.

What survives model replacement is the examiner: the failures turned into tests, the rules that change the next edge, and the track record that lets a machine merge its own work. Install one skill, pull 25 traces, and build one eval today. Add another whenever something breaks.
