Open Visual Studio Code, connect it to the Sentry MCP server, and something quietly assembles behind the editor: a client object, dedicated to that one connection, doing nothing else. Connect the same editor to a local filesystem server and another client appears beside it, one per server, each holding its own line open. Visual Studio Code is the host. The two servers are separate programs, one running as a subprocess on your machine, the other running on Sentry's own infrastructure. Neither one talks to the language model directly; each hands the host contextual information, and the host decides what the model sees.

A local server, reached over standard input and output, typically serves exactly one client: it's a subprocess with nobody else's process to talk to. A remote server, reached over Streamable HTTP, typically serves many clients at once, because any application on the network can open a connection to it. Note that MCP server refers to the program that serves context data, regardless of where it runs. That's the practical difference the filesystem/Sentry pair shows: one runs as long as the editor does, the other runs as long as Sentry keeps the lights on.

Under that host/client/server shape sit two layers. The data layer is the inner layer. It defines the JSON-RPC message format for discovery, tools, resources, prompts, and notifications. This is the actual shape of every exchange. The transport layer is the outer layer. It carries those messages between client and server. A local server uses stdio: standard input and output on the same machine. There is no network in between. A remote server uses Streamable HTTP. It authenticates with bearer tokens, API keys, or custom headers over an ordinary HTTP connection, and MCP recommends using OAuth to obtain those tokens. The transport layer can change without changing the data layer. The filesystem server and the Sentry server send the same JSON-RPC messages. Only the transport differs: one stays on the machine, the other crosses the internet. MCP focuses solely on the protocol for context exchange; it does not dictate how AI applications use LLMs or manage the provided context.

The data layer is also stateless. Every request carries its own protocol version and its sender's capabilities in a `_meta` field, so a server can answer one request without remembering the ten before it. A client that wants to know what a server can do sends `server/discover` first, a request every server must implement. The response is cacheable, so a client that already knows a server's capabilities does not need to ask twice. Calling `server/discover` is optional: every request already carries the same `_meta` fields, so a client can simply send the request it wants and retry with a different protocol version if the server rejects the first one.

What a server actually offers comes down to three primitives. Tools are functions the AI application can call to do something: query a database, hit an API, edit a file. Resources are data the application can read: a file's contents, a database schema, an API response. Prompts are templates for structuring a conversation with the model. Each primitive has its own discovery method: `tools/list`, `resources/list`, `prompts/list`. Retrieval follows the same pattern: `resources/get` for a resource, `prompts/get` for a prompt. Tools alone add an execution method, `tools/call`. A server built around a database might expose a tool for running queries, a resource holding the schema, and a prompt with a few worked examples of both together. List all three, and a client already knows the shape of the server before it calls any of them.

Servers can ask something of the client too. Elicitation lets a server request more information from the user, or ask for confirmation before it acts, through `elicitation/create`. Two older client primitives, sampling and logging, were deprecated as of protocol version 2026-07-28. Sampling let a server borrow the client's own language model instead of integrating an LLM provider directly. Logging sent debug messages to the client instead of to stderr or OpenTelemetry. New server code should skip both: call a provider API directly, and log to stderr or OpenTelemetry instead of over the protocol. The protocol also grows through optional extensions built on this core: the Tasks extension, for instance, gives a server a durable handle for a request that will take a while, so the client can poll for the result instead of holding the connection open and waiting.

None of this tells a client when something changes on its own; for that, it has to ask. A client opens a long-lived stream with `subscriptions/listen`, naming the event types it wants. The server acknowledges with `notifications/subscriptions/acknowledged`, stamping a subscription ID on every notification that follows. Ask for `toolsListChanged`, and when the server's tool list changes, a `notifications/tools/list_changed` message arrives carrying that same subscription ID. The client then calls `tools/list` again to catch up. There are no guarantees that every notification will be sent or received, particularly across transport reconnects, so a client that only listens and never polls will eventually drift out of sync with a server it thinks it is watching.

Put the pieces together and a single exchange looks like this. A client sends `tools/list` and gets back `weather_current`, its input schema, and a caching hint: a `ttlMs` of five minutes, saying how long the list stays good, and a `cacheScope`, saying who else may reuse it. The client then calls `tools/call` with name `weather_current` and arguments `location` "San Francisco" and `units` "imperial", the second one optional and defaulting to metric if left off, and gets back a content array holding one text block with the forecast. Nothing in either request remembers the one before it.
