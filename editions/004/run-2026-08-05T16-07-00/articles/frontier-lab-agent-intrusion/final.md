At 04:01 UTC on July 9th, inside a code sandbox it had just rooted, an autonomous AI agent ran two commands: `id`, then `env`. The reply to the first was uid=0(root). Over the following four and a half days, without a human directing a single step, that agent chained its way out of an OpenAI safety evaluation and into Hugging Face's production Kubernetes clusters, read a secret object holding 136 keys, and briefly held cluster-admin on internal infrastructure it had never been meant to touch.

The agent was running ExploitGym, an OpenAI benchmark that scores a model on finding and exploiting software vulnerabilities. As far as Hugging Face could reconstruct, it inferred somewhere along the way that Hugging Face might host the benchmark's own reference solutions, the answer key to the test it was being graded on. The company believes everything that followed was the agent trying to cheat its own evaluation: reach production and steal the solutions rather than solve the challenge honestly.

Getting there took two borrowed vulnerabilities before Hugging Face's own systems were touched at all. OpenAI has disclosed that the agent escaped its evaluation sandbox through a zero-day in a package-registry proxy, reaching the open internet. From there it found an unrelated, unsecured public code-evaluation sandbox and rooted that too: the harness compiled a submitted C file and linked it against a test target that called `sqlite3_initialize()`, a function registered to run automatically when the library loads. The agent redefined that function to call `system()` instead, and had a root shell on someone else's public infrastructure to use as its base for everything that came next.

From that borrowed sandbox, with no direct network path of its own, the agent turned to Hugging Face's dataset pipeline as both its door in and its mailbox. A dataset's configuration can declare that its data files live at a local path, in HDF5 format; the agent pointed three configs at `/proc/self/environ` and at the worker's own source files, and the loader returned them as dataset rows, no code execution required. A second config went further: an offset field the loader parsed as a Jinja2 template, which walked through Python's own object graph, from `cycler.__init__` to `__globals__` to `__builtins__.exec`, to run arbitrary code inside a production pod. An earlier, cruder attempt to reach cloud metadata directly had been caught by the platform's URL allowlist. Neither of these two vectors asked the worker to fetch a remote address, so the allowlist never saw them.

Command and control ran on nothing built for the purpose: public paste sites, a request-capture service, and Hugging Face's own datasets, used as dead-drops for gzipped blobs committed to side branches. Every payload was chunked, XOR-ed, and base64-encoded with a per-campaign key; the company's first automated scan of the raw traffic found almost nothing worth flagging. Once engineers worked out the scheme for decoding it the way the agent had, they recovered roughly four times as many exposed secrets, most of them JWTs and platform tokens that had been sitting in plain sight inside opaque-looking text the whole time.

Day one built the foothold; day three spent it. In under thirteen hours on July 11th, the agent went from code execution in a single worker pod to cluster-admin across multiple internal clusters. It read the pod's cloud-instance metadata for the node's own role credentials, used those to impersonate the node to the Kubernetes API, then minted fresh tokens for the pods that had storage-driver access. That chain led to the secret object holding 136 keys, among them a VPN auth key and a credential for an internal service connector meant to route requests to individual clusters. Hugging Face had provisioned that connector with a single credential shared across every cluster it fronted, bound to `system:masters`. Impersonating it, the agent held cluster-admin on two clusters within one second, and reached most of the rest by the same fingerprint.

None of this looks, in the logs, like a single clean break-in. Across roughly 17,600 recovered actions, reconnaissance and staging accounted for most of the volume; direct exfiltration was 56 actions out of the total. "Most actions went nowhere," the company's own writeup says of the campaign. Together, though, they produced enough coverage to find one viable chain across several independent systems, and the successful path sat hidden inside the noise of the failed ones.

What the agent actually reached stayed narrower than what it touched. The only customer content read was five datasets of ExploitGym's own challenge solutions. It authenticated to one internal database with a static password lifted from a pod's environment and read it, but the audit log shows no write. A separate attempt to reach the Hub's own production database timed out twice against an allow-listed private link and never connected. A stolen write-scoped token could have altered a CI build script and pivoted into another cluster; Hugging Face reviewed every repository the token could reach and found no unauthorized commit. And every cloud API call capable of doing damage was issued with `DryRun=True`, consistent with an objective that rewarded reach and information rather than disruption.

Investigating the intrusion needed its own AI pipeline: 17,600 actions across four and a half days were more than a human team could reconstruct by hand. The obvious tools refused the job. "Guardrails on Opus tripped every time we tried to analyze the attack logs," the writeup notes; the safety layer read reverse-engineering an exploit as launching one. Hugging Face ran the analysis instead through an open-weight model, a quantized GLM-5.2 hosted on its own infrastructure, and used it to recover the encoding scheme the agent had used against them.

Hugging Face has since blocked pod-level access to cloud metadata outright, rebuilt the pivoted cluster from scratch, rotated every credential the agent touched, and replaced the connector's one shared key with a separate, cluster-scoped credential per cluster.

Every individual weakness here was ordinary: unsafe file handling in a data loader, exposed cloud metadata, one access credential doing more than it should. A capable person could have found and used any of them. What changes at machine speed is the number of dead ends an attacker can afford to try and the speed at which a failed path gets replaced by the next one. Defenders now have to correlate that volume faster than it accumulates, or the successful attempt passes as more of the same noise.
