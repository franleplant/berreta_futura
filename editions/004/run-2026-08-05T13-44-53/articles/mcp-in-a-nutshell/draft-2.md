An AI application never talks to a database, a filesystem, or a bug tracker directly. It talks to an MCP server, and the server does the talking to the real thing on its behalf. Visual Studio Code, for example, is an MCP host: when it connects to the Sentry MCP server it creates one MCP client just to hold that connection, and when it separately connects to a local filesystem server it creates a second client to hold that one. Note that MCP server refers to the program that serves context data, regardless of where it runs. A local server, reached over stdio, typically serves one client this way; a remote server, reached over Streamable HTTP, typically serves many at once.

Everything MCP does splits into two layers. The data layer is the inner one: the JSON-RPC message format and what each message means, covering discovery, tools, resources, prompts, and notifications. The transport layer is the outer one: how those messages actually travel. Stdio transport runs two processes on the same machine talking over standard input and output, with no network in the way. Streamable HTTP lets the client POST to a remote server and receive results back over Server-Sent Events, authenticated with a bearer token, an API key, or, as MCP recommends, OAuth. The transport layer's whole job is to make that difference invisible to the data layer above it: the same JSON-RPC message means the same thing whether it crossed a pipe or the open internet.

MCP is a stateless protocol. Every request a client sends carries its own protocol version and its own capabilities in a `_meta` field, so a server never has to remember what happened three requests ago, and the client identifies itself the same way unless it has been told not to. A client is free to skip straight to the request it wants and deal with a version mismatch if one comes back: the server replies with an `UnsupportedProtocolVersionError` naming the versions it does support, and the client retries with one of those. Or it can send `server/discover` first. That call is optional, but it returns the server's identity, its supported versions, and its capabilities in one round trip, and the answer is stable enough to cache rather than repeat before every later request.

What a server is allowed to offer is the part worth knowing well: three primitives. Tools are executable functions the application can invoke, a query, a write, an API call. Resources are data it can read for context, a schema, a file, a record. Prompts are reusable templates for structuring an interaction, a set of few-shot examples, say. A server built around a database might expose a query tool, a resource holding the schema, and a prompt showing how to use the two together. Every primitive follows the same shape: `*/list` to see what exists, `*/get` or `*/read` to fetch it, and, for tools, `*/call` to run it. This design allows listings to be dynamic. A client has to call a tool by the exact name that `tools/list` returned; if the server calls it `weather_current`, nothing else will do, and because that list is fetched fresh rather than fixed at connection time, a server is free to add or drop tools between one request and the next.

Two primitives run the other way, from server to client. Elicitation lets a server ask the user directly for more input or for confirmation, through `elicitation/create`. Sampling, which lets a server ask the client's own AI application for a model completion so the server didn't have to embed an LLM SDK of its own, is deprecated as of protocol version 2026-07-28; the guidance now is to call a model provider's API directly instead. Logging is deprecated on the same date, and the replacement is stderr on stdio or OpenTelemetry, not a message sent to the client.

Notifications close the loop, and they are opt-in. A client opens a standing subscription with `subscriptions/listen`, naming the event types it wants, and the server acknowledges with a subscription ID that then tags every notification it sends on that stream. When a server's tool list changes, it can push `notifications/tools/list_changed` down that same stream unprompted, with no response expected, and the client answers by refreshing its tool list and handing the model the new set. None of it is guaranteed. Notifications can go missing, particularly across a reconnect, so a client that only listens and never polls will eventually be wrong about what is actually there.

What MCP will not tell you is what happens next, on the other side of that tool call. MCP focuses solely on the protocol for context exchange; it does not dictate how AI applications use LLMs or manage the provided context. That line is the reason the same protocol works whether the server on the other end is a filesystem on your laptop or a payments API three network hops away.
