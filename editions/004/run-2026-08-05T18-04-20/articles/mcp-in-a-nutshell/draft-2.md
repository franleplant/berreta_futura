MCP gives an AI application a common way to reach tools and data without deciding how that application uses a language model or manages the context it receives. A host such as Visual Studio Code connects to servers through clients, and each client keeps one dedicated connection to its server. A local filesystem server may run as a process on the same machine over standard input and output. Sentry’s official server runs remotely over Streamable HTTP. Both are MCP servers; location changes the transport, not the role.

MCP has two layers. The data layer uses JSON-RPC 2.0, a standard format for sending requests and responses, to define message structure, the handshake that identifies supported versions and features, and the primitives servers and clients can offer. The transport layer establishes connections, frames messages, and handles authentication. Stdio is direct process communication with no network overhead. Streamable HTTP uses HTTP POST, can stream with Server-Sent Events, and supports ordinary HTTP authentication methods such as bearer tokens, API keys, and custom headers. The same JSON-RPC message format travels through either mechanism.

MCP is a stateless protocol. Every request carries the protocol version and the capabilities relevant to that request in its `_meta` field. Clients normally include `clientInfo` there as well. A client may begin with the mandatory `server/discover` request, which carries fields such as `protocolVersion`, `clientInfo`, and `clientCapabilities`. The server replies with its identity, capabilities, and a `supportedVersions` list. If the requested version is refused with `UnsupportedProtocolVersionError`, the client retries with a version both sides support. Discovery is typically cacheable and optional: because the metadata travels with every request, a client can send another request directly and handle a version error if one comes back.

The important question is what a server can actually offer. MCP defines three server primitives. Tools are executable functions for actions such as file operations, API calls, and database queries. Resources provide context such as file contents, database records, and API responses. Prompts are reusable templates for structuring interactions with language models. Clients discover them with methods such as `tools/list`, `resources/list`, and `prompts/list`; where appropriate, they retrieve or execute them with methods such as `*/get` and `tools/call`. A `tools/list` request may include a pagination cursor. Its response describes each tool with a `name`, human-readable `title`, `description`, and JSON-Schema `inputSchema`, along with caching metadata such as `ttlMs` and `cacheScope`; the example permits a five-minute freshness period. Listings may change over time, so discovery is dynamic.

Consider a database server. It might expose a tool for querying the database, a resource containing its schema, and a prompt with few-shot examples for using the tool. The client first learns what exists, then the application can combine tools from many connected servers into one registry for the language model. When the model chooses a tool, the application routes the call to the client connected to the right server and returns the result as conversation context. A concrete call uses JSON-RPC with an `id`, the method `tools/call`, and parameters such as `name: "weather_current"` and `arguments: {"location": "San Francisco", "units": "imperial"}`. The same `_meta` envelope carries the protocol version, client identity, and client capabilities. The tool name must match discovery exactly, and its arguments must follow the advertised schema. The response can contain several content objects, including text, images, or resources.

Servers can also ask the user for more information or confirmation through elicitation. Sampling and logging are deprecated client primitives as of protocol version 2026-07-28. New implementations should call language-model providers directly rather than use sampling, and should write logs to stderr for stdio transport or use OpenTelemetry. Optional extensions can build on the core protocol. The Tasks extension, for example, lets a server return a durable handle for a long-running request so the client can poll for a result later.

Notifications keep a client’s view current without requiring constant polling. A client opts in by opening a long-lived `subscriptions/listen` stream with a filter such as `"toolsListChanged": true`. The server replies with `notifications/subscriptions/acknowledged`, including a `subscriptionId` and only the notification types it agrees to honor. A tools-list notification is available only when the server declared `listChanged: true` in its tools capability and the client requested that filter. When the available tools change, the server sends `notifications/tools/list_changed` without an `id`, as required for a JSON-RPC notification, and includes the subscription ID so the client can associate it with the right stream. The client normally responds by requesting `tools/list` again and updating the model’s available capabilities.

These updates are best effort. A reconnect may lose a notification, so clients should also rely on polling to preserve freshness of results. MCP supplies a shared vocabulary and message flow; the application remains responsible for deciding what the model may do with the context it receives.
