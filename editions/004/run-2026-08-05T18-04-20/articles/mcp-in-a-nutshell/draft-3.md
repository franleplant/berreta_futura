MCP gives an AI application a common way to reach tools and data without deciding how that application uses a language model or manages the context it receives. A host such as Visual Studio Code connects to servers through clients, and each client keeps one dedicated connection to its server. A local filesystem server may run as a process on the same machine over standard input and output. Sentry’s official server runs remotely over Streamable HTTP. Both are MCP servers; location changes the transport, not the role.

MCP has two layers. The data layer uses JSON-RPC 2.0 to define message structure, version and capability discovery, and the primitives servers and clients can offer. The transport layer establishes connections, frames messages, and handles authentication. Stdio is direct process communication with no network overhead. Streamable HTTP uses HTTP POST, can stream with Server-Sent Events, and supports bearer tokens, API keys, and custom headers. MCP recommends OAuth for obtaining authentication tokens. The same JSON-RPC message format travels through either mechanism.

MCP is stateless. Think of each request carrying its own small passport. Its `_meta` field includes `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities`; clients normally add `io.modelcontextprotocol/clientInfo` as well. A client may begin with the mandatory `server/discover` request. The server answers with `io.modelcontextprotocol/serverInfo`, its capabilities, and `supportedVersions`. If it rejects the requested version with `UnsupportedProtocolVersionError`, the client retries with one both sides support. Discovery is typically cacheable and optional: because the metadata travels with every request, a client can send another request directly and handle a version error if one comes back.

The useful question is what a server can offer. Tools let an AI application perform actions such as file operations, API calls, or database queries. Resources supply context, including file contents, database records, and API responses. Prompts package reusable interaction templates, such as system prompts or few-shot examples. Clients find these through methods such as `tools/list`, `resources/list`, and `prompts/list`, then retrieve or execute them with methods such as `*/get` and `tools/call`. A `tools/list` request may include a pagination cursor. Its response gives each tool a `name`, a human-readable `title`, a `description`, and a JSON-Schema `inputSchema`, plus caching metadata such as `ttlMs` and `cacheScope`. Listings may change over time, so discovery is dynamic.

Consider a database server. It might expose a query tool, a resource containing the database schema, and a prompt with few-shot examples for using that tool. The client first learns what exists; then the application can combine tools from many connected servers into one registry for the language model. When the model chooses a tool, the application routes the call to the client connected to the right server and returns the result as conversation context.

The concrete request in the protocol example uses a weather tool, but the shape is the same for the database query: JSON-RPC supplies an `id` and the `tools/call` method; parameters name the tool and provide arguments. The name must match discovery exactly, and the arguments must follow the advertised schema. The same `_meta` envelope carries the protocol version, client identity, and client capabilities. A response can contain several content objects, including text, images, or resources.

Beyond this main exchange, MCP has optional and advanced features. Servers can request more information or confirmation from users with `elicitation/create`. Sampling, through `sampling/createMessage`, and logging are deprecated client primitives as of protocol version 2026-07-28. New implementations should call language-model providers directly rather than use sampling, and should write logs to stderr for stdio transport or use OpenTelemetry. Extensions can build on the core protocol; the Tasks extension, for example, gives a server a durable handle for a long-running request so the client can poll for the result later.

Notifications keep a client’s view current without requiring constant polling. A client opts in by opening a long-lived `subscriptions/listen` stream with a filter such as `"toolsListChanged": true`. The server replies with `notifications/subscriptions/acknowledged`, including a `subscriptionId` and only the notification types it agrees to honor. A tools-list notification is available only when the server declared `listChanged: true` in its tools capability and the client requested that filter. When the available tools change, the server sends `notifications/tools/list_changed` without an `id`, as required for a JSON-RPC notification, and includes the subscription ID so the client can associate it with the right stream. The client normally requests `tools/list` again and updates the model’s available capabilities.

These updates are best effort. A reconnect may lose a notification, so clients should also rely on polling to preserve freshness. MCP supplies the shared message flow and the boundary around context and capability; the application still decides what the model may do with them.
