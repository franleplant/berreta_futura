Consider a database MCP server. It may expose a query tool, a resource containing the database schema, and a prompt with few-shot examples for interacting with those tools. An AI application acts as the MCP host. The host creates one MCP client for each server and coordinates them. Each client maintains a dedicated connection to its corresponding server. A local MCP server using STDIO typically serves a single client. A remote MCP server using Streamable HTTP typically serves many. Wherever it runs, the server is the program that provides context. MCP focuses solely on the protocol for context exchange. The AI application decides how to use its LLMs and manage the context the protocol provides.

The exchange has two layers. The data layer defines message structure and semantics. MCP uses JSON-RPC 2.0 as its underlying RPC protocol. Clients and servers exchange requests and responses. Notifications can be used when no response is required. The transport layer establishes connections, frames messages, and handles authentication. STDIO uses standard input and output to connect local processes, with no network overhead. Streamable HTTP sends client-to-server messages with HTTP POST. Optional Server-Sent Events provide streaming. The transport supports bearer tokens, API keys, and custom headers. MCP recommends OAuth to obtain authentication tokens. The transport layer abstracts communication details from the protocol layer, enabling the same JSON-RPC 2.0 message format across all transport mechanisms.

Return to the database server’s next request. MCP writes method names with a slash, such as `server/discover`. In `*/list` and `*/get`, the asterisk stands for the primitive being listed or retrieved. Each request also carries a metadata object called `_meta`, which contains the protocol version and the capabilities relevant to that request. Clients should identify themselves there unless configured not to. This makes MCP stateless: each request stands on its own. A client may call `server/discover` before any other request to learn the server’s supported versions, capabilities, and identity. Every server must implement it. If the requested version is unsupported, the server rejects the request with the versions it accepts. The client retries with a mutually supported version. Discovery is optional. A client may send another request first and handle a version error. The response is typically cacheable. The client need not repeat the initial exchange for every request.

On the server side, primitives carry actions, context, or interaction templates: tools are executable functions, resources are data sources, and prompts are reusable templates. Clients use `*/list` to discover them and `*/get` to retrieve them. The client invokes a tool with `tools/call`. In the database example, the query tool performs the action, the schema resource supplies context, and the prompt provides few-shot examples for the interaction. The tool name must match the discovered definition exactly. Its arguments must follow `inputSchema`, a JSON Schema that defines the expected parameters. A tool result contains an array of content objects. Text, images, and resources may all appear there. The application may add that content to the model’s conversation. This design allows listings to be dynamic.

On the client side, `elicitation/create` lets a server request more information or confirmation from a user. Sampling and logging are deprecated client primitives as of protocol version 2026-07-28. New implementations should integrate directly with LLM provider APIs. For logging, new STDIO implementations should write to stderr. Other implementations should use OpenTelemetry. For long-running requests, the optional Tasks extension lets a server return a durable handle. The client polls that handle for status and retrieves the result later.

The AI application keeps a notification stream open for the changes it cares about. For the database server’s tools, the client opens a long-lived `subscriptions/listen` stream and names the event types it wants. Change notifications are opt-in. A server that advertises support for changed tool lists acknowledges the subset it will honor. After that acknowledgment, the server sends `notifications/tools/list_changed` when its available tools change. The message has no `id`. Under JSON-RPC, no response is expected. When one arrives, the application normally requests `tools/list` again and updates the tool registry available to the model. Notifications are best effort. The protocol gives no guarantee that every notification will be sent or received, especially across a transport reconnect. Clients should also rely on polling when they need fresh results. The same pattern extends beyond tools to the other primitives, keeping clients and servers synchronized in real time as their available capabilities change.
