Start with a database request. The Model Context Protocol (MCP) lets a database server expose a query tool, a resource containing its schema, and a prompt with a few examples for using those tools. The AI application plays host: it opens one MCP client per server, each with a dedicated connection. A local server usually serves one client when standard input and output (STDIO) carry the messages. A remote server typically serves many clients over Streamable HTTP. MCP defines only the context exchange. The application decides how to use its language models and the context they receive.

Inside that connection, JSON-RPC 2.0 supplies the message format. Requests and responses travel through it, while notifications carry updates that need no reply. The transport layer moves messages between local processes or remote machines, frames them, and handles authentication. STDIO connects local processes without network overhead. Streamable HTTP sends client-to-server messages with HTTP POST and can add Server-Sent Events for streaming. It accepts bearer tokens, API keys, and custom headers. MCP recommends OAuth for obtaining authentication tokens. Both transports carry the same JSON-RPC 2.0 format.

Now let the host ask the database server what it supports. MCP spells methods with a slash: `server/discover` asks for discovery. The wildcard forms `*/list` and `*/get` describe primitive listing and retrieval. For resources, the concrete methods are `resources/list` and `resources/read`. Every request carries a `_meta` object with the protocol version and the capabilities relevant to that request. Clients normally put their identity there too. Those fields let the server process each request on its own, which makes the protocol stateless. Every server implements `server/discover`, though a client may skip the call and handle a version error on its next request. The discovery response reports supported versions, capabilities, and identity. If the client asks for an unsupported version, the server returns an error listing the versions it accepts. The client retries with one they share. The response is typically cacheable, letting the client reuse it instead of repeating discovery for every request.

With discovery in hand, the client sends `tools/list` and builds a registry from the response. Each tool supplies a name, title, description, and `inputSchema`, a JSON Schema that defines its arguments. To call one, the client passes that exact name to `tools/call` and supplies arguments matching the schema. The server returns an array of content objects. An object may carry text, an image, or a resource, and the host can add the result to the model’s conversation. Tool listings can change. An application connected to many servers can discover them progressively rather than load every tool at once.

If the database server needs more information or confirmation before running a query, it can request it with `elicitation/create`. The protocol marks sampling and logging as deprecated client primitives as of protocol version 2026-07-28. To get a language-model completion, a new server should integrate directly with a provider’s API. For logging, new STDIO implementations should write to stderr, while other implementations should use OpenTelemetry. The optional Tasks extension lets a server return a durable handle for a long-running request. The client can poll that handle for status and retrieve the result later.

Tool availability can change while the conversation runs. To hear about those changes, the client opens a long-lived `subscriptions/listen` stream and sends a `toolsListChanged: true` filter. The server can honor that filter only if its tools capability advertises `listChanged: true`. It replies with `notifications/subscriptions/acknowledged`, placing `io.modelcontextprotocol/subscriptionId` in `_meta`. Later `notifications/tools/list_changed` messages carry the same ID. Those notifications carry no JSON-RPC `id`, so the server sends no response. Change subscriptions are opt-in and best effort. A reconnect may lose an event, and the client should call `tools/list` again when it needs a fresh registry. The same subscription pattern can cover the other primitives. If the client skips that poll, the model may continue with an old tool list.
