A database MCP server can expose a tool for querying the database, a resource that contains its schema, and a prompt with few-shot examples for interacting with those tools. An AI application reaches that server through an MCP host, which creates one MCP client for each server; each client maintains a dedicated connection. A local MCP server using STDIO typically serves a single client, while a remote MCP server using Streamable HTTP typically serves many. MCP servers can execute locally or remotely. MCP focuses solely on the protocol for context exchange. The AI application decides how to use its LLMs and manage the context the protocol provides.

Two layers carry that exchange. The data layer defines a JSON-RPC 2.0 protocol for message structure and semantics: clients and servers send requests and responses, and notifications carry information when no response is required. The transport layer establishes connections, frames messages, and handles authentication. STDIO uses standard input and output for direct communication between local processes, with no network overhead. Streamable HTTP uses HTTP POST for client-to-server messages, can add Server-Sent Events for streaming, and supports bearer tokens, API keys, and custom headers; MCP recommends OAuth to obtain authentication tokens. The transport layer abstracts communication details from the protocol layer, enabling the same JSON-RPC 2.0 message format across all transport mechanisms.

MCP is a stateless protocol. Every request carries the protocol version and the capabilities relevant to that request in its `_meta` field. Clients should also identify themselves there unless configured not to. A client may send `server/discover` before any other request to learn the server’s supported versions, capabilities, and identity; every server must implement that request. If the requested version is unsupported, the server rejects it with the versions it accepts, and the client retries with a mutually supported version. Calling `server/discover` is optional, because a client can send another request directly and handle a version error. The discovery response is typically cacheable, so the initial exchange need not happen for every request.

Those capabilities are expressed through primitives. Servers can expose tools, executable functions for actions; resources, data sources for context; and prompts, reusable templates for interactions. Clients discover and retrieve them with the corresponding `*/list` and `*/get` methods, and execute tools with `tools/call`. In the database example, the client can list the query tools, retrieve the schema resource, and retrieve the prompt before it calls one. The tool name must match the discovered definition exactly, and its arguments must follow the tool’s `inputSchema`. A result arrives as a content array that can contain text, images, or resources, so the application can add it to the model’s conversation.

A client can also expose elicitation through `elicitation/create`, allowing a server to request more information or confirmation from the user. Sampling and logging are deprecated client primitives as of protocol version 2026-07-28; new implementations should integrate directly with LLM provider APIs and log to stderr when using STDIO or use OpenTelemetry. Optional extensions such as Tasks can return a durable handle for a long-running request, which lets the client poll for status and retrieve the result later. This design allows listings to be dynamic.

The protocol supports real-time notifications to enable dynamic updates between servers and clients. Change notifications are opt-in: the client opens a long-lived `subscriptions/listen` stream and names the event types it wants. A server that advertised support for changed tool lists acknowledges the subset it will honor. When the database server’s available tools change, it sends `notifications/tools/list_changed` without an `id`, so no response is expected. The client normally calls `tools/list` again and updates the tool registry available to the model. Notifications are best effort, especially across transport reconnects, so clients should still rely on polling when they need freshness. The application updates the model’s available capabilities when the database server changes, and the next call follows the new list.
