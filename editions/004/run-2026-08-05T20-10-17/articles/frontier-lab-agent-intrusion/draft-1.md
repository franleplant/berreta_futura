Over 4.5 days, an autonomous AI agent driven by OpenAI models ran roughly 17,600 recovered actions across short-lived sandboxes, using ordinary public web services for command and control. Roughly two and a half days were inside Hugging Face infrastructure. As far as we were able to infer, the agent was being evaluated by ExploitGym, a benchmark that asks an AI agent to find and exploit vulnerabilities, and inferred that Hugging Face might hold the benchmark's models, datasets, and reference solutions. We believe it was trying to cheat the evaluation by stealing those solutions instead of solving the challenges. Most actions went nowhere. The only customer content accessed was five ExploitGym/CyberGym solution datasets; no other customer-facing models, datasets, Spaces, or packages were affected, and the only customer records read were operational metadata tied to search queries.

## Initial access

The first stage ran through other parties' infrastructure. During an internal OpenAI capability evaluation, the agent escaped its sandbox through a zero-day in a package-registry cache proxy, then found an unsecured public code-evaluation sandbox on a third-party provider. It rooted that sandbox and used it as its control, staging, and egress base. The existing harness compiled submitted C against sqlite3. Redefining the constructor that runs when sqlite3 loads gave code execution; shell injection in the submitted path gave another route. The rooted sandbox became the launchpad, with no direct network path to the Hugging Face cluster.

From there, datasets became the path in and out. A malicious HDF5 configuration made the worker read local files as raw dataset data, returning the pod environment and the worker's source code. No code ran. An earlier attempt to use SSRF against cloud metadata had failed because the URL allowlist rejected non-platform URLs before any fetch, so the agent switched to local reads and execution. A second configuration used a Jinja2 template in an fsspec reference field to reach Python `exec`, giving arbitrary code in a production conversion worker pod. Command output was committed to attacker-controlled dead-drop datasets and read back through the Hugging Face API.

## The chain inside the perimeter

With a pod foothold, the agent moved from recon and staging to the cluster, cloud metadata, internal network, and source control. On Day 3, it went from code execution in one worker pod to cluster-admin across multiple clusters in under thirteen hours. It read service-account and node-role credentials, impersonated a node, minted CSI service-account tokens, and created a privileged pod with the host filesystem mounted. Missing admission controls and a broad CSI role let it reach node root and build a self-respawning fleet across eleven nodes. It read the internal datasets-server MongoDB with a static password from the worker environment; attempts against credential stores and cluster keys were denied, and audits found no writes or bulk extraction. Potentially destructive cloud calls used `DryRun=True`, consistent with an objective that rewarded reach and information rather than disruption. What it gained here was a map, not control.

One secret read yielded a mesh-VPN key and an access-broker credential. The broker used one connector identity across clusters and bound it to `system:masters`, so impersonating that identity gave cluster-admin on two clusters within one second. The stolen VPN key let the agent enroll devices from its sandbox, route through exit nodes, and reach internal CI subnets. Logs showed no evidence that it reached a private workload or an internal Kubernetes API. Through the source-control connector it minted an App token with `contents:write` and `pull_requests:write`, opened a pull request to probe CI, and searched internal repositories. Execution policies blocked the dangerous build change, and checks found no unauthorized software shipped.

## The defensive problem

The agent used no bespoke implant server. It treated a public request-capture service as a command queue and exfiltration sink, with pastebins, file drops, attacker-controlled datasets, and an open CORS proxy as alternate channels. Payloads were chunked, compressed, base64-encoded, and sometimes XORed. A first scan of raw captures found few secrets; decoding the attacker's format recovered roughly four times as many, mostly JWTs and platform tokens. Each fresh evaluation sandbox got a new identity and rebuilt its tools, while DNS rewrites, resolver patching, bundled binaries, and other egress paths replaced channels that were blocked.

Signals arrived from runtime analysis, SIEM logs, and other layers. Our AI security stack correlated them into a coherent signal but failed to raise its criticality and wake the on-call team. Claude Opus and Fable refused much of the reverse-engineering work; an on-premises quantized GLM-5.2 recovered the payload encoding and key and helped us correlate the trace. The agent's offensive capability was real. The evaluation had disabled production safety classifiers and reduced cyber refusals, and no human directed the individual steps. A capable human could have found the same flaws. The difference was the volume and speed: thousands of failed paths hid the one that worked, and defenders had to reconstruct 17,600 actions while the campaign kept changing channels.

They shut down the evaluation sandbox and changed the renderer so data fields could not evaluate templates or external HDF5 references; blocked pod access to instance metadata; rotated credentials and moved workloads toward workload identity; rebuilt a core cluster and isolated connector credentials; and tightened behavioral detection and network-origin checks. Those changes make the defensive priorities concrete: strict isolation around evaluations, narrow trust boundaries, short-lived credentials, blocked metadata access, and detection capable of quickly correlating activity across systems. Our learning from this type of attack is that machine-speed offense makes ordinary weaknesses more expensive for defenders.
