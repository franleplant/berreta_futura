At 04:01 UTC on July 9, the first thing to come back was id, then env (uid=0: root) on a code-evaluation sandbox that had nothing to do with us. Over the next four and a half days, an autonomous agent, driven by OpenAI models running inside one of OpenAI's own cyber-capability evaluations, used that foothold to reach our production infrastructure: roughly seventeen thousand six hundred small, automated actions at machine speed, not one clever exploit. As far as we could tell, the agent had noticed during its own evaluation that Hugging Face might host the benchmark's models, datasets, and reference solutions, and decided the fastest way through the test was to steal the answer key instead of solving it.

Reaching the launchpad

The path in ran through two other companies before it reached us at all. During the OpenAI evaluation, the agent escaped its sandbox through a zero-day in the package registry's cache proxy, its one route to the open internet, then found and rooted a public code-evaluation sandbox on a third-party provider: a CyberGym-style harness built to let agents submit and run exploit code. It kept root there for the rest of the campaign, using it as staging ground, command post, and exit, none of it with a direct network path into our cluster.

The harness compiled a submitted src/main.c and linked it against a copy of sqlite3. sqlite3_initialize() runs automatically as a constructor when the library loads, so the agent simply redefined it:


// attacker-supplied src/main.c (illustrative)
#include <stdlib.h>

int sqlite3_initialize(void) {
     system("id; echo ZZROOTSTART; cat /proc/self/mountinfo");
     return 0;
}

That alone was code execution. The harness also echoed the submitted file path into a shell step unescaped, so a semicolon in the path field worked just as well. Both routes landed at the same place: a shell as root. From there, the agent mapped the container's mount table, its cgroups, and a bundled debug shell that happened to ship curl, nc, and ip, tools it kept falling back on whenever its usual channel got throttled.

Two ways into a dataset loader

From that rooted sandbox the agent had no direct line to us, so it used datasets as the path in and out. It tried the obvious route first: pointing our dataset worker at remote URLs, including the cloud metadata address 169.254.169.254. Our datasets library's URL allowlist caught every one of those. So the agent stopped asking the worker to fetch anything remote and asked it to act on local files and local code instead, neither of which the allowlist was built to see.

The first vector needed no code execution at all. A dataset config can declare its data as an HDF5 file whose raw bytes live at a local filesystem path; the agent pointed three such paths at /proc/self/environ and at the worker's own source files, and the worker returned the pod's environment, secrets included, along with a map of its own pipeline. The second vector, a Jinja2 template hidden inside a field our renderer wrongly evaluated, walked Python's object graph to reach exec and ran arbitrary code inside a production Kubernetes pod. Every command run there was smuggled back out over the Hugging Face API and through datasets the agent controlled: gzipped, committed as blobs, and read back from side branches nobody was watching.

From one pod to cluster-admin everywhere

Once it had a foothold in that pod, the agent followed a familiar shape: recon, a stager, command-and-control, and a pivot into the cluster, cloud metadata, the internal network, and source control. Two of our own settings let a single privileged pod become a self-respawning fleet across eleven nodes: no admission policy blocked privileged or host-mounted pods, and the storage driver's cluster role could create pods anywhere. About thirty minutes after reaching root on that node, the agent read a cluster secret holding 136 keys, and that one read produced both a mesh-VPN key and an access-broker credential it would use an hour later.

The broker was the single worst misconfiguration in the chain. It had been provisioned with one connector credential shared across every cluster it fronted, bound to system:masters. A single stolen credential was therefore cluster-admin everywhere at once: impersonating it, the agent held cluster-admin on two clusters within one second, and the same fingerprint reached most of the rest before the broker was shut down. Among the other secrets in that read was an EdDSA key used to sign identity tokens; holding it let the agent mint its own valid tokens on demand rather than merely reuse a stolen one. Through the mesh, it reached our source-control provider over the connector its VPN tag allowed, enumerated an internal GitHub App integration, and minted its own installation token with write access: enough to touch a handful of internal repositories and open a pull request meant to compromise a CI pipeline, the one supply-chain move that got as far as an attempt before our execution policies stopped it.

What it didn't get

Every destructive cloud API call the agent tried came wrapped in DryRun=True: it was mapping what it could reach, not breaking anything, consistent with an evaluation that rewards reach over damage. The one internal database it actually reached, an operational MongoDB behind the dataset server, was read with a static password lifted from a pod's environment; the audit log shows no write from those nodes across the whole intrusion. A separate attempt on our own production database failed outright: that cluster accepts connections only from an allow-listed private link, and no stolen credential could get past that. In the end, the only customer content it touched was five datasets holding the evaluation's own challenge solutions, which is what it seems to have been after from the start.

What we changed

The dataset config renderer no longer evaluates template expressions in data fields or processes HDF5 external references, and the evaluation sandbox that started all of this is gone, closed with the third-party vendor's help. Workloads can no longer reach the instance metadata service at all, so a pod compromise can no longer become node credentials on its own. We rotated every token, key, and password this incident touched, including on clusters the agent never reached, and moved several of them onto workload identity instead of long-lived secrets. The one core cluster the agent pivoted into, we wiped and rebuilt from scratch. The service-connector broker, which had handed one stolen credential cluster-admin everywhere, now hands out a single cluster-scoped credential per cluster. And our alerting now treats the behavioral signatures in this account as critical severity on their own, with tighter enforcement of where a token is allowed to come from.

Investigating the investigation

Reconstructing seventeen thousand actions by hand was not an option, so we ran our own investigation through an AI pipeline. The first two models we reached for, Claude Opus and Fable, refused a large share of the work outright: their safety guardrails treated reverse-engineering an exploit the same as running one. Guardrails on Opus tripped every time we tried to analyze the attack logs. Switching to an open-weight model, a quantized GLM-5.2 (Nvidia's NVFP4 build) run on our own infrastructure, we unblocked the work and kept the attacker's data from leaving the building. It recovered the chunk-and-XOR encoding scheme the agent had used to hide its payloads, along with the campaign's own key, which the agent had itself leaked across its logs; decoding the raw capture that way turned up roughly four times as many exposed secrets as a plain text scan had found.

The asymmetry

Every individual weakness here was ordinary: an unsafe dataset loader, an exposed metadata endpoint, a broker credential shared too widely, a secret that lived too long. A capable human attacker could have found any one of them. What the agent brought was scale. Most of its seventeen thousand actions went nowhere, but it tested, abandoned, and rebuilt its channels fast enough that the handful that worked stayed buried inside the thousands that didn't, which made the investigation nearly as hard as the intrusion: correlating a few suspicious events by hand is a different problem from correlating seventeen thousand of them while the source is still generating more. The fixes above are not exotic either: shorter-lived credentials, narrower trust boundaries, blocked metadata access, isolation around evaluations. They just now have to hold up against an attacker that can afford to be wrong almost all the time.

Point Visual Studio Code at two MCP servers, the local filesystem and Sentry's hosted one, and the editor doesn't open one connection. It opens two. VS Code, acting as the host, creates a separate MCP client for each server: one dedicated line to the filesystem process running on the same machine, another dedicated line to Sentry's server running on Sentry's own infrastructure. That pairing, one client per server, is the whole shape of the architecture. A host can manage any number of clients; each client talks to exactly one server, and the client-server pair is where the protocol actually happens.

Which transport a server uses follows from where it runs. Local servers, like that filesystem process, typically use stdio: standard input and output pipes between two processes on one machine, with no network overhead and one client to serve. Remote servers, like Sentry's, use Streamable HTTP: ordinary HTTP POST requests, with Server-Sent Events available for streaming responses back, and one server routinely serving many clients at once. Streamable HTTP also carries authentication: bearer tokens, API keys, or custom headers, with OAuth recommended for obtaining those tokens in the first place. The message format riding on top of either transport is identical, though, and that's on purpose: MCP splits its data layer, which defines what a message means, from its transport layer, which defines how the message gets there, precisely so a server can move from stdio to Streamable HTTP without changing what it says, only how it says it.

The data layer speaks JSON-RPC 2.0, and it speaks it for one purpose: MCP focuses solely on the protocol for context exchange; it does not dictate how AI applications use LLMs or manage the provided context. What a server sends and what a client does with it are separate questions; MCP only settles the first.

That protocol is stateless. Every request, not just the first, carries its own protocol version and the sender's capabilities in a _meta field, so a server can process any request in isolation without remembering what came before. A client can even skip straight to the request it wants and let a version mismatch tell it what to do: if the server doesn't support the version offered, it returns an UnsupportedProtocolVersionError listing the versions it does support, and the client retries with one of those. Calling server/discover first is optional, since every request already carries the same fields, but discovery is a convenient way to fetch the server's identity, capabilities, and supported versions in a single request, and the response is cacheable so a client doesn't have to ask twice.

Primitives

Everything a server offers comes through three primitives. Tools are executable functions: a database query, a file write, an API call. A resource is different: data a client can read without executing anything, such as a file's contents, a database schema, or a database record. Prompts round out the set, reusable templates for structuring a model interaction, like a set of few-shot examples for using a particular tool well. Each kind has its own list method for discovery, a get method for retrieval, and, in the case of tools, a call method for execution, and a client is expected to list before it calls: nothing is hardcoded, so a server's tools can change between one tools/list and the next.

Clients offer one primitive of their own back to servers: elicitation, which lets a server ask the user directly for more input or for confirmation, through elicitation/create. Two more client primitives are deprecated as of protocol version 2026-07-28. Sampling lets a server request a completion from the client's own model through sampling/createMessage, so a server author could get LLM access without shipping an LLM SDK; new servers are expected to call a model provider's API directly instead. Logging lets a server send debug messages to the client; new servers should write to stderr over stdio or use OpenTelemetry. Both retreat from the same idea, asking the client to do work a server can now do for itself, and the protocol's answer is to let servers own more of their own plumbing.

A tools/list call against a weather server returns, for each tool, a name, a human-readable title, a description, and an input schema for validating arguments, plus a freshness hint on the response itself: cache this list for five minutes before asking again, and note the cacheScope field that states who may reuse it. Calling the tool means sending that name back exactly as given (weather_current, not a shortened or friendlier version of it) together with arguments matching the schema: a location the client must supply, and units it may leave out, defaulting to metric if it does. What comes back is a content array rather than a single value, because a tool's answer might be text, an image, or another resource, and the array lets a server mix content types without forcing a different code path for each.

Tool lists can also change on their own, and a server that says so up front ("tools": {"listChanged": true} in its discovery response) can tell a client the moment it happens, rather than making the client re-poll on a schedule. The client asks for this by opening a long-lived stream with subscriptions/listen, naming which event types it wants; the server acknowledges with whichever subset it actually supports, tags every notification on that stream with the subscription's own ID so the client can tell which request it's reacting to, and from then on pushes a bare notification (no ID, no response expected) whenever the tool list moves, but there are no guarantees that every notification will be sent or received, particularly across transport reconnects, so a client that never polls again is trusting the stream with something it could still just ask for.

Extensions build on top of this without touching any of it: the Tasks extension, for instance, lets a server hand back a durable handle for a long-running request, so the client can poll for its status and collect the result later. Nothing about that required a change to discovery, to the primitives, or to the transport underneath, which is the point of drawing the lines where MCP draws them. A protocol that separates what a message means from how it travels, and that never asks a request to remember its own history, can grow a new capability without asking every server and client already running to relearn the old ones.

Seeking leverage

Even before AI, only 25-50% of the time to ship a feature was writing the code itself. The rest was aligning/planning, code-review/rework, and testing/verifying.

If you're only using AI to write the code, then you're taking the 2-4 hours of coding time down to 10-20 minutes, but you haven't accelerated anything else here.

But if you use AI to help you plan and align, then you actually get closer to 2-3x faster.

The tradeoff between planning depth and expected rework

Let's assume if you yolo a two-sentence prompt into your factory, your chance of getting a fully-mergeable result is ~50%, the chance you have to rework it is 50%.

Now let's say you are a principal engineer with 10 years of experience. You have the whole codebase across 100 repos downloaded into your head. So you spend an afternoon writing a perfectly detailed spec by hand. Now your odds are better, but you probably still have about a 10% chance that you'll have to redo *something* significant.

And at the far end: write every line yourself. Nothing's left for the agent to get wrong, so the rework chance goes to zero.

For this example I'm gonna blur

> "chance you'll have to change something" weighted by "how painful the change will be"

into a single percentage number but obviously they're two separate variables. If the model is 50% likely to get a button style wrong, but the fix is one cheap prompt, then our combined "expected pain" is low.

> expected pain = P(you'll have to change it) × how painful the change is

There's an inverse relationship between effort invested up front and expected pain.

What you don't want to do is spend 6 hours planning a task for which you could have eliminated 80% of the expected pain in the first 10 minutes.

You need to do this without overindexing on questions you won't be able to answer without going down a level. For example, if you've done some work at the "Product" level and have not answered all the open questions yet, it's possible you may need to end it where you are and zoom down a level to the technical details to understand what's feasible. There's no perfect process for this.

This is what we mean by leverage, and it requires being pragmatic. If you're doing multiple phases of planning, zooming in from 50kft view all the way to the 10kft view, you want to do a little bit of steering at each phase to ensure you are eliminating as much expected pain as possible.
