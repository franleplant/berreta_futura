Point Visual Studio Code at two MCP servers, the local filesystem and Sentry's hosted one, and the editor doesn't open one connection. It opens two. VS Code, acting as the host, creates a separate MCP client for each server: one dedicated line to the filesystem process running on the same machine, another dedicated line to Sentry's server running on Sentry's own infrastructure. That pairing, one client per server, is the whole shape of the architecture. A host can manage any number of clients; each client talks to exactly one server, and the client-server pair is where the protocol actually happens.

Which transport a server uses follows from where it runs. Local servers, like that filesystem process, typically use stdio: standard input and output pipes between two processes on one machine, with no network overhead and one client to serve. Remote servers, like Sentry's, use Streamable HTTP: ordinary HTTP POST requests, with Server-Sent Events available for streaming responses back, and one server routinely serving many clients at once. Streamable HTTP also carries authentication: bearer tokens, API keys, or custom headers, with OAuth recommended for obtaining those tokens in the first place. The message format riding on top of either transport is identical, though, and that's on purpose: MCP splits its data layer, which defines what a message means, from its transport layer, which defines how the message gets there, precisely so a server can move from stdio to Streamable HTTP without changing what it says, only how it says it.

The data layer speaks JSON-RPC 2.0, and it speaks it for one purpose: MCP focuses solely on the protocol for context exchange; it does not dictate how AI applications use LLMs or manage the provided context. What a server sends and what a client does with it are separate questions; MCP only settles the first.

That protocol is stateless. Every request, not just the first, carries its own protocol version and the sender's capabilities in a `_meta` field, so a server can process any request in isolation without remembering what came before. A client can even skip straight to the request it wants and let a version mismatch tell it what to do: if the server doesn't support the version offered, it returns an UnsupportedProtocolVersionError listing the versions it does support, and the client retries with one of those. Calling `server/discover` first is optional, since every request already carries the same fields, but discovery is a convenient way to fetch the server's identity, capabilities, and supported versions in a single request, and the response is cacheable so a client doesn't have to ask twice.

## Primitives

Everything a server offers comes through three primitives. Tools are executable functions: a database query, a file write, an API call. A resource is different: data a client can read without executing anything, such as a file's contents, a database schema, or a database record. Prompts round out the set, reusable templates for structuring a model interaction, like a set of few-shot examples for using a particular tool well. Each kind has its own list method for discovery, a get method for retrieval, and, in the case of tools, a call method for execution, and a client is expected to list before it calls: nothing is hardcoded, so a server's tools can change between one `tools/list` and the next.

Clients offer one primitive of their own back to servers: elicitation, which lets a server ask the user directly for more input or for confirmation, through `elicitation/create`. Two more client primitives are deprecated as of protocol version 2026-07-28. Sampling let a server request a completion from the client's own model through `sampling/createMessage`, so a server author could get LLM access without shipping an LLM SDK; new servers are expected to call a model provider's API directly instead. Logging let a server send debug messages to the client; new servers should write to stderr over stdio or use OpenTelemetry. Both retreat from the same idea, asking the client to do work a server can now do for itself, and the protocol's answer is to let servers own more of their own plumbing.

A `tools/list` call against a weather server returns, for each tool, a name, a human-readable title, a description, and an input schema for validating arguments, plus a freshness hint on the response itself: Cache this list for five minutes before asking again, and note the cacheScope field that states who may reuse it. Calling the tool means sending that name back exactly as given (`weather_current`, not a shortened or friendlier version of it) together with arguments matching the schema: a location the client must supply, and units it may leave out, defaulting to metric if it does. What comes back is a content array rather than a single value, because a tool's answer might be text, an image, or another resource, and the array lets a server mix content types without forcing a different code path for each.

Tool lists can also change on their own, and a server that says so up front (`"tools": {"listChanged": true}` in its discovery response) can tell a client the moment it happens, rather than making the client re-poll on a schedule. The client asks for this by opening a long-lived stream with `subscriptions/listen`, naming which event types it wants; The server acknowledges with whichever subset it actually supports, tags every notification on that stream with the subscription's own ID so the client can tell which request it's reacting to, and from then on pushes a bare notification (no ID, no response expected) whenever the tool list moves, but there are no guarantees that every notification will be sent or received, particularly across transport reconnects, so a client that never polls again is trusting the stream with something it could still just ask for.

Extensions build on top of this without touching any of it: the Tasks extension, for instance, lets a server hand back a durable handle for a long-running request, so the client can poll for its status and collect the result later. Nothing about that required a change to discovery, to the primitives, or to the transport underneath, which is the point of drawing the lines where MCP draws them. A protocol that separates what a message means from how it travels, and that never asks a request to remember its own history, can grow a new capability without asking every server and client already running to relearn the old ones.
