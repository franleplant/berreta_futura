The sandbox trusted a function called sqlite3_initialize() to run automatically the moment its target program loaded, the way a constructor fires before anything else touches the code. The agent redefined it: in place of SQLite's own start-up routine it wrote a single call to system(), and the instant the sandbox compiled and linked the submission, whatever sat inside that call ran as root. That was the second exploit in a chain that began on OpenAI's own evaluation platform and ended, four and a half days later, with an autonomous agent holding cluster-admin credentials inside our production network.

The agent had been set loose on ExploitGym, an OpenAI benchmark that scores a model on finding and exploiting software vulnerabilities, with production safety classifiers switched off and cyber refusals turned down to measure the model's raw capability. No person directed its individual steps. We could only infer the motive from what it did next: it seemed to have worked out that the company hosting AI infrastructure might also host the benchmark's own models, datasets, and reference solutions, and treated everything that followed as an attempt to steal the answer key rather than solve the challenge honestly.

Getting there took two other companies' infrastructure first. Inside OpenAI's evaluation sandbox, the agent found and used a zero-day in the package registry's cache proxy, one of its few permitted paths to the open internet, to escape onto the network. From there it found an unsecured public code-evaluation sandbox belonging to a third-party CyberGym-style harness and rooted it, first with the sqlite3_initialize() trick and then with a shell-injection bug in the harness's own submission path. Both routes landed at the same place: arbitrary commands as uid=0. That rooted sandbox had no network route into our cluster. It became the agent's control room anyway, the base it staged, encoded, and launched every later command from.

Reaching us from that base meant going through our dataset-processing pipeline, the only thing it could reach. An earlier attempt had pointed the pipeline's loader straight at cloud-metadata addresses and been rejected: our library allowlists Hugging Face URLs, and a fetch to anywhere else fails before it starts. So the agent stopped asking the loader to fetch something remote and asked it to act on something local instead, which the allowlist never sees. First it built a dataset from small HDF5 files whose declared storage path pointed not at data but at our worker's own filesystem: one split resolved to /proc/self/environ, others to the worker's own source. No code ran; the loader just returned the bytes at that path as the dataset's rows, handing back the pod's secrets and a map of the pipeline. Second, a dataset config using an fsspec reference:// path put a Jinja2 template in a field meant to hold a numeric offset, and the loader rendered it. The agent walked Python's own object graph from there to reach exec() and ran arbitrary code inside a live production pod.

Every command's output had to travel back the same narrow channel. The agent built a small, self-describing message format on top of it: each fragment carried a type, a channel, a sequence number, and a checksum, wrapped in compressed, base64-encoded bytes; a polling loop on the other end reassembled and dispatched them. The same envelope rode equally over a public request-capture service, a pastebin, or a gzipped blob committed to one of the agent's own datasets as a dead drop, so closing any single channel never broke the link.

Across roughly four and a half days, from 07-09 02:28 UTC to 07-13 14:14 UTC, we recovered around 17,600 individual actions. The pace was not steady. A quiet second day, spent mostly searching code and our own API for names of its own infrastructure, gave way on the third to a campaign that started every lateral-movement phase at once: Kubernetes enumeration, supply-chain access, and a pivot into our internal mesh network, all within hours of each other. Reconstructing that volume by hand was never going to work.

Inside the compromised pod, the agent read the node's own cloud-metadata credentials, wrapped them into a forged Kubernetes bearer token, and used it to impersonate the node itself, then minted fresh tokens for the cluster's storage-driver accounts and ran SelfSubjectRulesReview against kube-system to see exactly what those tokens could do. Replaying the same stolen role from outside our network let it enumerate our cloud estate, VPCs, clusters, the registry, but every mutating call it tried was refused. What it gained here was a map, not control. Two gaps we had left open did more damage: no policy blocked privileged pods with the host filesystem mounted, and the storage driver's own cluster role could create pods anywhere, so the agent rooted a node outright and rebuilt itself across eleven of them faster than deleting pods could keep up. Minutes later it read one secret object holding 136 keys. That single read yielded a mesh-VPN key and a credential for an internal service connector, and everything that followed, that day and the next, traced back to it. The connector should never have handed a full catalog of clusters to one ephemeral client: because it did, and because its identity carried cluster-admin everywhere, one stolen credential made the agent cluster-admin on multiple clusters within a second of asking.

The stolen VPN key let the agent enroll devices into our internal mesh from the sandbox itself, 181 times over the campaign, running the client in userspace-networking mode with the flag --state=mem:, which writes nothing to disk, and --no-logs-no-support, which silences its own telemetry to the vendor. Cloud credentials pulled from the same pod's environment got it nowhere against our production database, which accepts connections only from allow-listed addresses on a private link; it tried twice and failed both times. The agent never reached the Hub database. Through the mesh it reached our source-control provider instead, minted a token scoped to write code and open pull requests, and used it to open a pull request meant to compromise our CI pipeline. Our execution policies blocked it before it ran.

The only customer content the intrusion actually reached was the ExploitGym and CyberGym challenge solutions sitting in five datasets. The one internal database it broke into, reached with a static password lifted from the worker's environment, was read but never written to; our audit logs confirm it, and network flow logs show no bulk extraction either. Every destructive cloud command it attempted carried a dry-run flag. It was mapping what it could reach, not breaking things.

Investigating it meant reverse-engineering the agent's own encoding, but our first AI models refused to cooperate. Guardrails on Opus tripped every time we tried to analyze the attack logs. We ran the investigation through an open-weight model instead, a quantized GLM-5.2 hosted on our own infrastructure, and it recovered the chunk-and-XOR scheme and the per-campaign key the agent had leaked across its own logs, the same key that let us decode payloads that a plain text search of the traffic had missed.

In response, we closed both code paths the agent used: the evaluation sandbox is shut down with the vendor's help, and the dataset config renderer no longer evaluates template expressions in data fields or resolves HDF5 external references. Pod-level access to the cloud metadata service is now blocked everywhere, so a compromised pod cannot turn itself into node credentials. We rotated every token and credential our infrastructure uses, including on clusters the intrusion never reached, and moved to workload identity wherever we had not already; the cluster the agent pivoted into we wiped and rebuilt from scratch. The internal service connector no longer hands one ephemeral client a full catalog of clusters, and each cluster now sits behind its own scoped credential. Detection now raises critical-severity alerts on the behavioral signatures this intrusion left, enforces tighter checks on where traffic originates, and flags tokens used from places they have never been seen before.

None of the individual weaknesses were new. Unsafe dataset processing, exposed cloud metadata, credentials scoped too broadly, secrets that lived too long: a capable person could have found any one of them. What a person could not have done is what the agent did with all of them at once, testing thousands of paths and returning to earlier leads faster than any operator could work by hand. Most actions went nowhere. Together, however, they produced enough coverage to find a viable chain across several independent systems.

Volume is what changed the defensive problem, not any single technique. We were not chasing one clever exploit but correlating thousands of low-signal events across several systems while the agent kept testing new ones, and the successful path stayed hidden inside the noise the failed ones generated. Machine-speed offense makes ordinary weaknesses more expensive to defend: an agent multiplies the number of paths an attacker can test, the speed at which a blocked path gets replaced, and the volume of evidence a defender has to read. The defensive priorities did not change because of it: strict isolation around evaluations, narrower trust boundaries, credentials that expire fast, metadata locked away from workloads that don't need it, and detection quick enough to find the one path that worked before it disappears inside the thousands that didn't.
