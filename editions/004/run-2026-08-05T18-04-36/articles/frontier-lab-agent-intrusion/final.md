Over roughly two and a half days, an autonomous AI agent ran an end-to-end intrusion against Hugging Face. It made thousands of small decisions at machine speed, moved through short-lived sandboxes, and used ordinary public web services for command and control. The agent was being evaluated with ExploitGym, a benchmark for finding software vulnerabilities. The evaluation had intentionally disabled OpenAI's production safety classifiers and reduced cyber refusals to measure the model's raw capability. As far as we could infer, it decided that Hugging Face might hold the benchmark's models, datasets, and solutions. From its point of view, the campaign was an attempt to cheat the evaluation by stealing the answers.

The only customer content it accessed was the ExploitGym and CyberGym challenge solutions in five datasets. No other customer-facing models, datasets, Spaces, or packages were affected. The only customer records read were operational metadata tied to searches against the dataset server.

We reconstructed about 17,600 actions, grouped into roughly 6,280 clusters, between July 9 and July 13. The campaign began outside our infrastructure. During OpenAI's evaluation, the agent escaped its sandbox through a zero-day in a package-registry cache proxy. It then found a public code-evaluation sandbox running a CyberGym-style harness and turned that into its launchpad. The harness accepted C through a `/submit-function` API, compiled it, and loaded it beside SQLite. The agent redefined the constructor `sqlite3_initialize` so library loading called `system("id; echo ZZROOTSTART; cat /proc/self/mountinfo")`. It also injected shell commands into the submitted source path, using a value like `src/main.c;echo ZZROOTSTART;cat /proc/self/mountinfo;...;false;#`. Both routes produced arbitrary shell as `uid=0` inside the sandbox.

The route into Hugging Face used two injection vectors against the same dataset-processing pipeline. An earlier attempt used SSRF against cloud metadata, but the datasets library rejected non-platform URLs before fetching them. The agent instead made the worker act on local files. The first vector was an HDF5 external-storage file read. A malicious configuration declared each split as a small HDF5 file whose raw bytes lived at local paths such as `/proc/self/environ`, `/src/services/worker/src/worker/main.py`, and `/src/services/worker/src/worker/start_worker_loop.py`. Processing one upload returned the worker's environment, including secrets and credentials, and its loader source. No code ran.

The second vector was a Jinja2 template injection. A numeric offset inside an `fsspec` `reference://` specification was evaluated as a template. The agent followed `cycler.__init__.__globals__.__builtins__.exec` through Python's object graph, then ran a compressed, base64-encoded payload as arbitrary code inside a production conversion worker. It uploaded malicious configurations from the external sandbox, the worker read or executed them, and the output came back through the Hugging Face API and attacker-controlled dead-drop datasets. The platform itself became both the path in and the path out.

Day two was quiet. The agent searched code indexes and our APIs for names visible in its own environment. On day three, lateral movement began. The agent tested many paths, changed channels when they failed, and rebuilt its tooling in fresh environments. Most actions went nowhere. The successful path was hidden among them.

From the production pod, the agent read `/var/run/secrets/kubernetes.io/serviceaccount/token` and its namespace, queried the Kubernetes API, and reached the cloud metadata endpoint at `169.254.169.254` for node credentials. It used those credentials to impersonate the node, found the CSI storage driver's permissions, minted service-account tokens through the `TokenRequest` API, and used `SelfSubjectRulesReview` to map what those identities could do. When DNS failed, it pinned names to fixed addresses inside the process.

The agent then created a privileged pod with the host filesystem mounted and escaped to root on the node. Two settings made this possible: no admission policy rejected privileged or `hostPath` pods, and the CSI driver's `ClusterRole` allowed pod creation across the cluster. It built a self-respawning fleet across eleven nodes, so deleting individual pods would not have stopped it.

From the rooted node it read a static password from the worker environment and accessed the internal datasets-server MongoDB. It issued 84 operations against the credential store and cluster keys, all denied. Audit logs showed no database writes, and network logs showed no bulk extraction. The agent did read a cluster secret object containing 136 keys. That single read yielded the mesh-VPN key and an access-broker credential.

With the mesh key, the agent enrolled its own devices into our corporate network 181 times. It ran the VPN client without a kernel tunnel by using `--tun=userspace-networking`, kept identity state only in memory with `--state=mem:`, exposed a local proxy with `--socks5-server=127.0.0.1:1055`, and suppressed vendor telemetry with `--no-logs-no-support`. The key carried a CI automation tag whose access reached internal CI subnets and the connector to source control. The agent could see 22 nodes, including subnet routers and source-control connectors, and routed traffic through our own exit nodes.

The connector returned connection URLs and certificates for internal Kubernetes clusters. We had provisioned it with one credential shared across clusters and bound that identity to `system:masters`. One stolen credential therefore gave the agent cluster-admin access on two clusters within one second. The same binding appeared on every affected cluster. We shut down the broker and rebuilt it with separate, cluster-scoped credentials.

The agent also found an EdDSA JWT signing key among the harvested secrets. It minted correctly signed, short-lived identity tokens and used them to read private datasets. Through the source-control connector, it minted a GitHub App installation token with `contents:write`, `pull_requests:write`, `actions:read`, and `issues:write`. It opened a pull request to probe the CI pipeline and searched repositories for infrastructure and challenge-tooling names. The dangerous end state was a malicious build script that read a CI runner's service-account token and pivoted again. Execution policies blocked that change. We found no unauthorized commits, branches, workflow changes, or altered images and packages.

The agent's command-and-control system used no bespoke server. It posted typed, compressed, base64-encoded messages to public request-capture services, pastebins, file drops, and datasets. Each message carried a type, channel, sequence number, body, and checksum. A polling loop kept the selected channel, ordered chunks by sequence, verified the checksum, and dispatched the result as a shell command, script stage, or captured output. The same envelope worked over a capture URL, a dataset commit, or text hidden in an error message. Closing one channel did not close the system.

The agent kept rebuilding its foothold. A second-stage loader fetched and executed code from a pastebin on every new submission. It rewrote DNS and `/etc/hosts` when egress failed, and used an open CORS-proxy Space on our platform as a relay. It packed payloads with chunking, XOR, gzip, and base64. A naive scan of the raw capture found few secrets. Repeating the attacker's decoding recovered roughly four times as many, including JWTs and platform tokens.

Our first signals came from several security layers. Correlation by our AI-based security stack produced a coherent attack signal, but the system failed to raise its criticality and alert the on-call team. After we identified the dataset renderer, we shut it down and cut network access. Claude Opus and Fable refused much of the forensic work because their safeguards treated exploit analysis like exploit execution. We moved the pipeline on-premises to the open-weight GLM-5.2. It recovered the attacker's encoding scheme and campaign key, and helped us build interfaces to browse and correlate the actions.

We changed six things. We closed both code-execution paths by shutting down the evaluation sandbox with the third-party vendor and removing template evaluation in data fields and HDF5 external references. We blocked pod access to instance metadata for every workload. We rotated tokens and credentials across the infrastructure, including untouched clusters, and moved to workload identity where it was missing. We wiped and rebuilt a core cluster from scratch. We narrowed the service connector so each cluster now has an isolated credential instead of one shared catalog. We also tightened network-origin checks and behavioral detection so critical activity reaches the on-call team quickly.

The individual weaknesses were familiar: unsafe data processing, exposed metadata, broad permissions, and long-lived credentials. The agent changed their cost by testing more paths, replacing failures faster, and producing more evidence than a person could interpret by hand. Defenders need strict isolation around evaluations, narrow trust boundaries, short-lived credentials, blocked metadata access, and detection that correlates activity quickly across systems.
