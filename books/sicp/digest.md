Harold Abelson and Gerald Jay Sussman argue that programming is a way of knowing how to do things, and that its real craft is keeping complexity under control. They name three tools for that: abstractions that hide detail, conventional interfaces that let standard parts snap together, and new languages when the old ones stop fitting the problem. The book starts from a handful of primitives and one rule for evaluating them. It climbs through higher-order procedures, data abstraction, generic operations, state and streams. Then it turns around and writes interpreters: a lazy one, a backtracking one, and a logic language. It ends at the register machine, the garbage collector and a compiler. One idea holds the whole thing together. An evaluator is just another program, and you can read it, change it and write it yourself.

## Knowing how

Abelson and Sussman begin by demoting syntax, clever algorithms and mathematical analysis. The essential subject, they say, is "the techniques used to control the intellectual complexity of large software systems." In practice that means knowing what not to read, what not to understand at the moment, and how to change a system safely. They offer three means of control and treat them as common to all engineering. Abstractions hide detail. Conventional interfaces let well-understood pieces be combined in a mix-and-match way. New languages bring out particular aspects of a design. The third gets an early mention: in any very large task, inventing languages is a good way to isolate the traffic between modules. Big systems tend to grow embedded languages near their human interfaces, and Lisp's syntax is so trivial to parse that building language processors costs almost nothing.

Computer science, in their view, is not really a science and has little to do with computers. It is procedural epistemology. Mathematics gives a precise framework for "what is." Computation gives one for "how to." Their example is the square root. You can define it as the y, not negative, whose square is x. That is a legitimate function, but it gives no way to find y. Newton's method does: guess, average the guess with x divided by the guess, and repeat until the guess is good enough. From 1 the square root of 2 goes to 1.5, then 1.4167, then 1.4142. The program splits into improve, good-enough? and an iterating procedure. It loops without any looping construct, using nothing but procedure calls, so this tiny language can already write any numerical program C or Pascal can.

From this the authors draw their most quoted rule: "programs must be written for people to read, and only incidentally for machines to execute." A language is a medium for ideas about method, so students should read long, well-written programs and change them in the spirit of the original author.

Alan Perlis's foreword adds a darker note. Every program is a model of a process only partly understood, so programs are never finished; they are revised until they sit inside some larger model. The processes they direct cannot be touched, yet they act on the world, and the novice is a sorcerer's apprentice. A small bug in a design program can bring down an airplane or a dam. Large programs cannot be fully proved correct, partly because their specifications are themselves doubtful. Reliability has to come from an arsenal of trusted idioms, combined by organizational techniques of proven value. Perlis also gives the line about data structures: it is better to have 100 functions operate on one data structure than 10 functions on 10. Pascal builds pyramids with armies pushing blocks. Lisp builds organisms.

Lisp has almost no syntax. Its formal rules can be taught in an hour, like the rules of chess, and then attention goes where it belongs, to decomposition and design. Combinations use prefix notation, so (+ 21 35 12 7) takes four arguments and nesting is never ambiguous. Deep nesting is hard on human eyes, which is why pretty-printing exists. The most significant feature is that procedures can be represented and manipulated as data. That blurs the line between passive data and active process and makes Lisp natural for writing interpreters and compilers.

Every powerful language, the authors say, has primitive expressions, means of combination and means of abstraction, and this holds for data as much as for procedures, which they hint are not really different things. The simplest abstraction is naming with define, as in (define circumference (* 2 pi radius)). Names need memory, and that memory is the environment. Without an environment it is meaningless to ask the value of (+ x 1), or even what + means.

Evaluating a combination is recursive: evaluate the parts, then apply the operator's value to the operands' values. Drawn as a tree, values percolate up from the leaves. A few special forms break the rule, each with its own. (define x 3) does not evaluate x. Cond and if handle case analysis. And and or are special forms because they may not evaluate every part, while not is an ordinary procedure. These exceptions, plus the general rule, are the whole syntax.

A procedure definition names a compound operation so it can be used as a unit. Square is (* x x); sum-of-squares is built from square; f from sum-of-squares; (f 5) gives 136. From outside, nobody can tell a defined procedure from a built-in one. Decomposition pays only when each piece does one nameable job. Split a program into arbitrary chunks and you gain nothing. A square built from exp, double and log is as good to good-enough? as one built from multiplication.

The substitution model explains application: replace each parameter by its argument and evaluate the body. (f 5) becomes (sum-of-squares 6 10), then (+ 36 100), then 136. The authors warn that this is a way to think, not how interpreters work. Normal order expands fully and then reduces; applicative order evaluates arguments first. For well-behaved procedures they agree. Lisp uses applicative order partly to avoid evaluating the same expression twice, as normal order does in (f 5), and mainly because normal order gets complicated outside this model. Exercise 1.5 shows how to tell the two apart, and normal order returns later in streams and a lazy interpreter.

Parameter names must not change meaning. Formal parameters are bound and can be renamed consistently. Free variables, like abs in good-enough?, connect a procedure to the outside world, and renaming a parameter to abs would capture it and introduce a bug. Block structure puts helpers such as improve and good-enough? inside sqrt, out of the global namespace. Under lexical scoping, free variables refer to the environment where the procedure was defined, so the helpers can use x directly. Section 1.1 is short and worth reading whole.


## The shapes of processes

Knowing the elements is like knowing how chess pieces move without knowing openings. An expert must foresee the process a procedure will generate, the way a photographer foresees a print. A procedure fixes only local evolution, how each stage follows from the last. The hard task is predicting global behavior, so the authors study a few typical shapes, using simple procedures as test patterns.

Recursive factorial, (* n (factorial (- n 1))), grows a chain of deferred multiplications and then shrinks it. Time and space both grow linearly. Iterative factorial carries everything in product, counter and max-count. You could stop it and resume it from those three values alone. The recursive version also depends on hidden information the interpreter keeps about where it stands in the chain. A footnote looks ahead: any iterative process can run on a machine with a fixed set of registers, while a recursive one needs a stack.

A recursive procedure is not a recursive process. Fact-iter calls itself, which is a fact about syntax, yet the process it generates is iterative. Scheme is required to be tail-recursive and runs such processes in constant space. Implementations of Ada, Pascal and C use memory with every call, which is why those languages need do, while and for. In Scheme, those constructs are only syntactic sugar.

Tree recursion arises when a procedure calls itself more than once. Steps grow with the number of nodes, space with the depth. Naive fib recomputes nearly half its work when computing (fib 5), and its steps grow as phi to the n. Yet tree recursion is often the natural formulation. The book counts the ways to change a dollar by splitting them into ways that skip the first coin and ways that use it. That gives 292 ways and no obvious faster method. Memoization, checking a table before computing, can turn such exponential processes linear. Count-change is the candidate named, and memo-fib later does the same for Fibonacci.

Order of growth, Θ(f(n)), measures how resources scale. Linear processes double when the input doubles; logarithmic ones add a constant. It is crude. It hides constant factors and assumes, for instance, that multiplying huge numbers costs the same as small ones, which is false.

Successive squaring computes b to the n in logarithmic steps: square b^(n/2) for even n, multiply once for odd n. Exponent 1000 needs 14 multiplications. For an iterative version the hint is to keep a·b^n invariant, and the authors call defining such an invariant "a powerful way to think about the design of iterative algorithms." Euclid's GCD replaces (a, b) with (b, a mod b): GCD(206,40) runs down to GCD(2,0) = 2. Lamé's Theorem ties its step count to Fibonacci numbers and shows it is logarithmic.

Primality can be tested by trial division up to √n, or by the Fermat test in logarithmic time. Expmod keeps numbers small by reducing modulo m at every step. The Fermat test is only probably right. Carmichael numbers, 561, 1105, 1729 and a few others, fool it, but they are rarer than hardware errors from cosmic radiation. The authors draw the moral: "Considering an algorithm to be inadequate for the first reason but not for the second illustrates the difference between mathematics and engineering." Variants such as Miller-Rabin cannot be fooled, and their error can be driven as low as you like, which opened the field of probabilistic algorithms. Fast primality testing is also why RSA works: a 200-digit number cannot be factored, but its primality can be checked in seconds.


## Procedures that take procedures

A language should let us name common patterns. Without cube we could compute cubes but not speak of cubing. Sum-integers, sum-cubes and pi-sum differ only in the term and next functions, and the authors put it plainly: "The presence of such a common pattern is strong evidence that there is a useful abstraction waiting to be brought to the surface." Make those functions parameters and you get sum, which is sigma notation as a procedure. (* 8 (pi-sum 1 1000)) gives 3.139592655589783, and sum then builds numerical integration.

Lambda makes procedures without names, and (define (plus4 x) (+ x 4)) is just a name bound to a lambda. Let is syntactic sugar for applying a lambda, so it needs no new machinery. Its value expressions are evaluated outside it: with an outer x of 2, (let ((x 3) (y (+ x 2))) (* x y)) gives 12. The authors use let for local variables and keep internal define for internal procedures, since internal definitions of values raise issues they treat later.

Procedures can also express whole methods. The half-interval method halves an interval where f changes sign; (half-interval-method sin 2.0 4.0) returns 3.14111328125. Fixed-point search applies f until values stop moving; (fixed-point cos 1.0) gives .7390822985224023, which the authors suggest checking on a calculator during a boring lecture. Seeking a square root as a fixed point of y ↦ x/y oscillates forever. Averaging y with x/y, which the authors call average damping, makes it converge and recovers the original square-root procedure.

Procedures that return procedures make transformations explicit. ((average-damp square) 10) gives 55. ((deriv cube) 5) gives about 75.00015. The old square-root method turns out to be a case of Newton's method, which is a fixed-point search on x ↦ x − g(x)/Dg(x). With deriv in hand, sqrt becomes newtons-method on y² − x.

The average-damp version of sqrt names three ideas: fixed-point search, damping, and y ↦ x/y. Cube root then needs only a new function. Both square-root methods collapse into fixed-point-of-transform, differing only in the transform passed. The authors add a caution: expert programmers choose the level of abstraction that fits the task and do not always write as abstractly as possible. All this rests on Lisp giving procedures first-class status, a notion due to Strachey. That costs implementers effort, because returned procedures must keep their free variables, but the gain in expressive power is enormous.


## Data, barriers and generic operations

Compound data raises the level at which we design, as compound procedures do. A rational number held as two loose integers forces you to track which numerator goes with which denominator. Glued into one object it becomes a unit, and a procedure like linear-combination, written with add and mul, works for rationals, complex numbers or polynomials alike.

Data abstraction separates use from representation, with constructors and selectors as the interface. The authors build rational arithmetic by wishful thinking: add-rat and its siblings are written using make-rat, numer and denom before those exist. Then a pair, built with cons and taken apart with car and cdr, supplies the representation, and one-half plus one-third prints 5/6. Pairs are the only glue needed. When one-third plus one-third prints 6/9, changing make-rat to divide by the GCD fixes it, and add-rat is untouched. The layers form abstraction barriers, each using only the interface below, so decisions like when to reduce can be deferred. The mobile exercise makes the same point by switching from list to cons and asking how much code must change.

What is data, then? A set of constructors and selectors plus conditions they must satisfy. For pairs: if z is (cons x y), (car z) is x and (cdr z) is y. Anything meeting that is a pair, including a cons that returns a dispatch procedure, with car calling it on 0. Procedures can represent data, and the line between them dissolves. Later the authors note that writing (wire 'get-signal) or (get-signal wire) is only a choice of sugar.

Closure is the next key. "Closure is the key to power in any means of combination," because results of cons can be consed again, giving hierarchies. Fortran and Basic arrays cannot hold arrays; Pascal and C structures need pointers and fixed fields. Lisp pairs are general glue, which is Perlis's maxim again. A list is a chain of pairs ending in nil, walked by cdring down and built by consing up, as in append. Length can be written recursively or iteratively. The expression (list 1 2 3 4) is not the list (1 2 3 4); evaluating the latter would try to apply 1.

Map captures the pattern of transforming each element. Its value, the authors say, is not that the computer does something new. It does the same thing. We think differently, and map sets a barrier between transformations and how elements are taken apart and joined. For-each does the same for effects such as printing. Lists of lists are trees: ((1 2) 3 4) has length 3 but four leaves. Count-leaves recurses on car and cdr, and the null? test must come before pair?. Map plus recursion gives scale-tree.

Then comes the chapter's central technique. Sum-odd-squares and even-fibs look unlike each other, yet both enumerate, filter, map and accumulate. Written conventionally, those stages are smeared through the code. Treat sequences as the signals between stages and the program becomes (accumulate + 0 (map square (filter odd? (enumerate-tree tree)))). Pieces then recombine into new programs, like engineers cascading standard filters. Programs now depend on a few sequence operations, so the representation can change, which the book later uses for infinite sequences. Waters found that 90 percent of the Fortran Scientific Subroutine Package fits this mold. Horner's rule, provably optimal, is an accumulation; dot products, matrix-vector products and transposes are short combinations of map and accumulate; fold-left and fold-right agree only for suitable operators. Nested loops become flatmap, which generates prime-sum pairs, permutations, and every solution to eight queens. When Louis Reasoner swaps the nested mappings in queens, the program recomputes earlier columns for every row and never finishes the six-by-six case. That chapter, 2.2.3, rewards reading in full.

The picture language shows the same ideas in miniature. It has one element, the painter, which draws a scaled image in any frame. Beside, below and the flips return painters, so wave2 is (beside wave (flip-vert wave)) and wave4 stacks two wave2s. Because combiners are ordinary procedures, abstraction comes free: flipped-pairs, right-split and corner-split are just procedures. One level higher, square-of-four takes four painter operations and returns one, capturing what flipped-pairs and square-limit share. A frame is an origin and two edges, and frame-coord-map sends (x, y) into it. Any procedure that draws in a frame is a painter, whether built from segments or a gray-level image. Flip-vert does not know how a painter works; it hands it an upside-down frame. This is stratified design: segments make painters, painters combine, combiners combine. A change to square-limit can be made at whichever level matches it, so small changes in specification need small changes in code.

Quotation lets symbols be data: with a and b bound, (list 'a b) gives (a 2). Eq? tests whether symbols are the same and supports memq. Symbolic differentiation, a problem that motivated Lisp, is written against sum?, addend and make-product before any representation is chosen, and then Lisp's own prefix notation serves. Raw results like (+ (* x 0) (* 1 y)) are ugly. Changing only make-sum and make-product to fold constants yields y, and deriv is not touched. What counts as simplest, the authors admit, depends on purpose.

Sets are defined by union, intersection, membership and adjoin, and here the representation matters for speed. Unordered lists make intersection Θ(n²). Ordered lists halve membership on average and make intersection Θ(n), since each step drops a head. Balanced trees make lookup logarithmic, but adjoining 1 through 7 in order yields a tree no better than a list, so balance must be maintained. The same techniques run keyed databases, and a quick unordered-list version can be swapped for a tree later without changing the rest of the system.

Huffman coding closes the section. Variable-length codes save bits when frequencies differ: a message that takes 54 bits in a fixed code takes 42 in a variable one. Prefix codes need no separators. The code is a tree with weighted leaves; left adds 0, right adds 1, and D is 1011. Huffman's algorithm repeatedly merges the two lightest nodes, kept at the front of a weight-ordered list, and the result is optimal though not unique. Procedures like weight, which handle leaves and trees, are early generic procedures.

That leads to the harder problem. Ordinary abstraction fails when one kind of data has several useful representations chosen independently by different people. Data abstraction applies the principle of least commitment, and the authors push it to keeping both choices at once. Complex arithmetic adds in rectangular form and multiplies in polar form. Ben uses rectangular, Alyssa polar, and the same arithmetic serves both. Type tags tell (3, 4) apart, magnitude 5 if rectangular, 3 if polar. Tags are stripped as data goes down into a package and attached as it comes up. Explicit dispatch on tags is not additive, though: every generic procedure must know every type, and names must be globally distinct.

The fix is to see a table of operations by types and work with it directly. Each package installs its procedures with put, inside an install procedure, so internal names never clash. Apply-generic looks up the operation and types and applies the result; (define (real-part z) (apply-generic 'real-part z)) never changes when types are added. Message passing slices the same table by columns: the data object is a procedure that receives an operation name. Chapter 3 depends on this.

The techniques build a generic system of ordinary, rational and complex numbers, with layered tags, and old rational code reused unchanged. Mixed types are harder. Writing one procedure per type pair works but undermines additivity. Coercion converts one argument to the other's type, and because the conversion depends only on types, one table suffices. Sometimes both must move to a third type. When types form a tower, integer to rational to real to complex, raising, inheriting operations and dropping become easy, and 2+3i plus 4−3i can come out as the integer 6. Real hierarchies are rarely towers; a triangle that is both isosceles and right has no unique way up. The authors are blunt that object-oriented languages have embodied inadequate theories of these relationships. Polynomials with generic coefficients recurse into any type, including other polynomials, with sparse term lists such as ((100 1) (2 2) (0 1)). Euclid's algorithm extends to polynomial GCDs with pseudodivision. But polynomials in x over y and in y over x sit in no tower, and the authors end with an honest admission: "we do not yet completely understand the concept of a data type."


## Objects that change

Large systems can be organized around objects whose behavior changes over time or around streams of information. Each choice raises its own language problems. Objects force us to deal with change and identity.

"An object is said to “have state” if its behavior is influenced by its history." A bank account's answer to a withdrawal depends on a history summed up in a balance. Set! plus a local variable builds such objects: each call to make-withdraw or make-account produces an independent account, and make-account dispatches on messages. The payoff is modularity. With a stateful rand, the Monte Carlo method becomes one procedure taking any experiment, and estimate-pi uses the Cesàro test cleanly. Without local state, random-gcd-test must thread the generator's values through its own loop. Rand-update is deterministic, so its numbers are pseudo-random, a question the authors leave to mathematicians and philosophers. The general lesson: to one part of a system, the others seem to have hidden state that changes with time, and programs can mirror that.

The price is high. (withdraw 25) twice gives 75, then 50, so procedures stop being mathematical functions. Without assignment, as in make-decrementer, they remain functions, and that is functional programming. With assignment the substitution model breaks: a variable now names a place whose contents can change, and substituting into make-simplified-withdraw wrongly returns 25. Referential transparency goes too. Two decrementers made the same way are interchangeable; two withdraw objects made the same way are not.

Sameness and change become circular: "Thus, we cannot determine “change” without some a priori notion of “sameness,” and we cannot determine sameness without observing the effects of change." Without mutation an object is the sum of its parts; with it, an account keeps its identity as the balance moves. Aliasing follows. If Paul's account is defined as Peter's, a change through one name shows through the other. Imperative factorial is right only if product updates before counter, a class of bug functional code cannot have. The authors find it ironic that beginners are taught imperatively, a habit they trace to the false belief that calls cost more than assignments, which Steele debunked. Assignment also makes evaluation order visible, and they insist no program should depend on it.

The environment model replaces substitution. An environment is a sequence of frames; a variable's value is its binding in the first frame that has one. Expressions mean nothing outside an environment, not even (+ 1 1). A procedure is code plus a pointer to the environment where its lambda was evaluated. Applying it builds a new frame binding parameters, enclosed by the procedure's environment, not the caller's. Define binds in the current frame; set! changes the first binding found or signals an error. Each call gets a fresh frame, so (f 5) makes separate frames for each square. When make-withdraw returns a lambda, the frame holding balance survives because the lambda points to it. That frame is where the state lives. W1 and W2 share code but not frames. Internal definitions work the same way, and in (sqrt 2) the helpers find x in the outer frame.

Mutable data needs mutators. Set-car! and set-cdr! build structures that cons cannot, and cons itself could be written from them and a fresh pair. Procedures with local state can implement mutable pairs, so assignment alone accounts for mutation. Sharing is invisible to cons, car and cdr but matters once mutation exists: z1 and z2 both print ((a b) a b), yet after set-to-wow! one prints ((wow b) wow b). Eq? tests identity, and mutators demand care. Queues with front and rear pointers give constant-time insertion. Tables use a dummy header as a fixed place to modify, nest into two dimensions with subtables, and can be objects holding their own lookup and insert!.

Two simulators show the style at scale. The digital circuit simulator is a language: gates are primitives, wiring is combination, and half-adder and full-adder are abstractions. Wires are objects with local state, and sharing them is how signals spread. An agenda of time segments, each with a queue of actions, drives an event-driven simulation in which the half-adder's sum becomes 1 at time 8. The constraint system goes further. It states relations, so the same Celsius-Fahrenheit network computes 77 from 25 and 100 from 212. Connectors wake their constraints, which set further connectors. Each connector remembers who set it, so only that informant can retract the value, and conflicting values raise "Contradiction (77 212)." An expression-style syntax like c+ is easy to layer over the imperative network; the reverse is very hard. Section 3.3 is worth reading through for these two programs.


## Time

Assignment forces time into our models. Before it, an expression always had the same value. Concurrency makes this worse, though it has real uses: writing as if concurrent avoids needless timing constraints, improves modularity, and can speed things up.

A single set! is a read, a compute and a write, and another process can slip between them. Peter withdraws 10 and Paul withdraws 25 from 100, and the balance ends at 75. The authors propose a sensible standard: results must match some sequential ordering, which may allow several correct outcomes, 70 or 90 for a deposit raced against a halving. Some problems, like heat diffusion, need even less.

Serializers allow only one procedure in a set to run at a time, so x*x and x+1 on 10 give only 101 or 121. They are built from mutexes, which rest on an atomic test-and-set!, the point where concurrency control truly enters. On modern pipelined, cached hardware that global flag is costly, and other methods are replacing it. Multiple resources are worse. Exchanging two accounts needs both serializers, which breaks modularity. Peter exchanging a1 with a2 while Paul exchanges a2 with a1 can deadlock. Havender's fix is to number resources and acquire them in order, but it fails when a process cannot know what it needs until it already holds something, and then systems must back out and retry.

In a distributed system a joint balance may be meaningful only right after synchronization. Barriers let processes run free between agreed points. Any notion of time in this setting depends on communication, as in relativity. Even test-and-set rests on an imperfect arbiter, because no fair arbiter can always decide in bounded time.

Streams offer another way. A quantity that changes, seen as a whole history x(t), does not change. Streams model state with no assignment at all, at a cost of their own. Lists are too eager for this: finding the second prime between 10,000 and 1,000,000 by filtering a list builds nearly a million integers. A stream builds only what its consumer asks for, and stops at 10,009. As an abstraction a stream is a list whose cdr is evaluated when selected instead of when built. Delay wraps an expression in a procedure of no arguments, force calls it, and memoization keeps repeated forcing from going exponential. Delayed evaluation separates the order of events from the shape of the program.

Streams can be infinite, because programs only ever look at a finite part. They can be defined in terms of themselves: ones is 1 followed by ones; integers adds ones to itself; fibs adds itself to its own cdr. The sieve of Eratosthenes is a processor that contains a copy of itself, a mirror inside a mirror. A primes stream can test primality using the primes stream itself. Hamming's numbers come from merging scaled copies of a stream, and power series become streams of coefficients, with sine and cosine defined from each other's derivatives.

An iterative process becomes a timeless stream of states, and whole sequences can then be transformed. Euler's transform, applied as a tableau, gets π to 14 places in eight terms where the raw series needs about 10^13. Infinite streams must be combined in an order that reaches every element, so interleave replaces append, and weighted merging yields Ramanujan numbers starting at 1,729. Streams also model signal processing directly. Feedback loops, though, need explicit delays, as in solving dy/dt = y to get 2.716924, and that splits procedures into two classes. Normal-order evaluation would remove the split. Delay and mutation mix badly, since delay hides when effects happen.

Streams give the modularity of hidden state without assignment: a stream of random numbers feeds a Monte Carlo procedure that needs no trial count. Stream-withdraw is a fixed function of its input, yet a user typing amounts sees a changing account. In the authors' words, "it is the user’s temporal existence that imposes state on the system." We build objects because, from inside a process, the rest seems to change, and objects make computer time mirror world time. Functional languages hoped to escape timing problems. But a joint account modeled with streams must merge Peter's and Paul's requests in real time, and merge is a relation rather than a function. The synchronization problem returns. The chapter ends without a winner: "We can model the world as a collection of separate, time-bound, interacting objects with state, or we can model the world as a single, timeless, stateless unity." Each view has strong advantages; neither alone satisfies, and no unification has appeared. Sections 3.4 and 3.5.5 are the book's most philosophical pages.


## Evaluators as programs

When problems outgrow a language, invent a new one. Electrical engineers move between a network language and a system language built on it. Almost any program is the evaluator for some language: the polynomial system, with read and print, is a language for symbolic mathematics, and so are the circuit simulator and the constraint propagator. Computer science becomes the discipline of building descriptive languages. The authors call one idea the most fundamental in programming: "The evaluator, which determines the meaning of expressions in a programming language, is just another program." With it in hand, a designer can try a new rule by editing the evaluator and mailing it to a colleague. The rest of the chapter does exactly that.

The metacircular evaluator is Scheme written in Scheme, and it is the environment model made concrete. Eval classifies an expression and directs its evaluation; apply runs primitives directly and evaluates compound bodies in an extended environment. The cycle between them is the essence of a language. The evaluator's job is not to define primitives, which it borrows from the host, but to supply the means of combination and abstraction that bind them into a language.

Eval uses abstract syntax, predicates like assignment? and selectors, so the concrete syntax can change without touching eval. Dispatch by a fixed cond means new forms require editing eval; data-directed dispatch avoids that. Cond becomes nested ifs and let becomes a lambda application; such derived expressions are what practical Lisps call macros. The implemented and implementing languages differ: true? translates truth between them. Operand order is inherited from the host's cons, the evaluator itself uses no higher-order procedures, environments are lists of frames scanned in turn, which is too slow for production, and primitives are tagged host procedures run from a driver loop.

A program describes an abstract machine, and the evaluator is a universal machine that configures itself to imitate it. A circuit that read a plan for a filter and became that filter is almost unimaginable; the evaluator is a fairly simple program. Any evaluator can emulate any other, so what can be computed does not depend on the language. Some things cannot be computed at all: given halts?, the procedure try, applied to itself, contradicts any answer. To the evaluator, (* x x) is just a list, and eval lets programs run data as code.

Internal definitions should have simultaneous scope, so mutually recursive even? and odd? make sense. Scanning them out into a let of unassigned variables does this, and in hard cases signaling an error is better than a wrong answer. Recursion is possible without define, by passing a procedure to itself, and the Y operator generalizes the trick. Separating analysis from execution makes the evaluator much faster: each expression is analyzed once into an execution procedure, instead of factorial rediscovering its own if on every call.

Lazy evaluation is the first variation. Arguments are delayed until a primitive needs them, so (try 0 (/ 1 0)) returns 1. A procedure is strict or non-strict in each argument. Constructors like cons are good candidates for laziness, and unless as a lazy procedure can be passed to higher-order procedures where a special form cannot. Arguments become thunks, an expression and its environment, forced on demand. The word comes from Algol 60 implementers, who said the expression had already been "thunk" about at compile time. Memoized thunks give call-by-need, which interacts confusingly with side effects, and laziness could be offered per parameter. With non-strict cons, lists and streams become one thing, and solve needs no explicit delays.

Nondeterminism is the second. Expressions can have several values, and the evaluator searches. Streams laid answers out in timeless sequence; amb makes time branch into possible histories. Amb picks an alternative, (amb) fails, and require is (if (not p) (amb)). Prime-sum-pair yields (3 20), (3 110), (8 35). Search is depth-first with chronological backtracking. The Dinesman puzzle falls out directly, faster when constraints come early. A parser of "The professor lectures to the student with the cat" finds both readings. Smarter schemes exist, dependency-directed backtracking and truth maintenance. Inside, execution procedures take success and failure continuations. Assignments install failures that undo them; unbound variables are bugs, not failures; and try-again simply calls the failure continuation.

Logic programming is the third. Most languages run one way, and constraint systems loosen that. A logic program states relations, so one set of append-to-form rules appends lists, finds a missing piece, and lists every split of (a b c d). The interpreter mirrors the Lisp one: eval and apply parts, frames of bindings. Queries are patterns; (job ?x (computer programmer)) finds Alyssa P. Hacker and Cy D. Fect. Dotted tails match the rest of a list. And, or and not mirror logic, and lisp-value admits Lisp tests. Rules stand for possibly infinite sets of assertions, read as implications. Matching extends a frame or fails. Unification lets both sides hold variables, solving simultaneous equations, and refuses a variable bound to an expression containing itself. Such a fixed-point binding resembles infinite series, where the same manipulation gives 2 in one case and a false sum in another.

Queries process streams of frames: and in series, or in parallel, not as a filter. Indexing by the leading symbol skips irrelevant entries, interleaving keeps infinite streams from starving others, and an and could merge independently computed frames. The worst case is still exponential. Applying a rule unifies with its conclusion and evaluates its body, like procedure application, with variables renamed per use in place of environments. Logic programming separates what from how by choosing a subset of logic weak enough to have a controllable procedural reading, a line descending from Robinson's resolution, Hewitt, Colmerauer and Kowalski. It is not mathematical logic. Clause order changes speed, some formulations run in only some directions, and sound rules can loop: (married Minnie Mickey) plus a symmetry rule sends a query around forever. No general scheme prevents this. The deepest gap is negation: "In the query system, however, “not P” means that P is not deducible from the knowledge in the data base." Run before its variables are bound, not filters out everything. Chapter 4 is the heart of the book.


## Down to the machine

The metacircular evaluator borrows its control from the host Lisp, so it cannot explain how values return or why some recursions run in constant space. Each model since Chapter 1, substitution, environment, metacircular, now register machine, has exposed questions the last one hid.

A register machine applies primitive operations to a fixed set of registers. Design means data paths plus a controller. The GCD machine needs a temporary register, since only one register changes per step. Read produces a value; print is an action, invoked by perform. A complex operation like rem can always be replaced by a loop of simpler ones. A textual language folds everything into the controller, which helps reading at the cost of hiding shared data paths. Subroutines store a return label in continue, which a subroutine calling another must save. Iterative processes need only registers. Recursive ones need a stack: save what you need afterward, solve the subproblem, restore, continue. Old values cannot in general be recomputed. The Fibonacci machine saves continue and n before one call, continue and val before the other.

A simulator builds machines from descriptions. The model is a message-passing object with registers, a stack and a pc driving an execute loop. The assembler does parsing and lookup once, turning instructions into execution procedures as the analyzing evaluator did. Every instruction but branch and goto advances the pc. Meters count pushes and maximum depth, measures of time and space.

Memory comes next. Pairs become indices into two vectors, the-cars and the-cdrs. Typed pointers carry tags, the old type-tag idea pushed down to the hardware. Symbols are interned so eq? compares pointers; whether eq? works on numbers depends on representation. Cons stores at free and increments it. Garbage collection keeps up the illusion of infinite memory by reclaiming whatever registers cannot reach. Stop-and-copy moves live pairs to fresh space, leaving a broken heart and forwarding address behind each, and flips the halves. It beats mark-sweep for large memories because it touches only useful data and compacts it.

The explicit-control evaluator recasts eval in seven registers and a stack. Eval-dispatch is a case analysis. Operands now go left to right, a decision the earlier model left open. Its data paths are universal, as a real computer's are. It saves only registers needed later, treats the last operand specially, and handles if and assignment by saving around one subevaluation. Its tail recursion is one jump: the last expression of a sequence goes to eval-dispatch with nothing saved. Save around it and iterative loops grow linearly, though they still compute the right values.

Interpretation simulates a program; compilation translates it. Compiled code is faster, interpreters easier to debug, so Lisp systems mix them. The authors put the contrast in one sentence: "An interpreter raises the machine to the level of the user program; a compiler lowers the user program to the level of the machine language." The compiler walks expressions as the interpreter does but emits instructions. Knowing what each subexpression does, it skips saves the interpreter must make for any contingency. Each generator takes a target register and a linkage: next, return or a label. Sequences record needed and modified registers, and preserving adds a save only when one matters. Branches combine in parallel, lambda bodies are tacked on, and val must not be preserved around a value being assigned. Compiled if branches around its true arm; lambda builds a procedure from a label and env; combinations build argl from the last operand back. Calls are declared to modify every register. Compiled (factorial 5) needs 31 pushes and depth 14 against 144 and 28 interpreted.

A call with target val and linkage return jumps without touching continue, so compiled code is tail-recursive. Most C and Pascal compilers are not. Open coding speeds primitives, though making + a reserved word is a bad idea. Lexical addressing finds variables by frame and offset. Dropping run-time checks, as C does, is fast and dangerous; the 1988 Internet Worm entered through an unchecked buffer. Compiled and interpreted code call each other through the evaluator. To port Lisp, translate the evaluator, or retarget the compiler and compile the compiler itself, checking that it reproduces its own output.
